Application-layer notes moved out of design-domain-model.md. The Application project is not started; read this note when its packs begin. Infrastructure items (Hangfire jobs, adapters) are kept here until that layer gets its own note.

OPEN

- Idempotency-Key header on write operations (S:API-IdempotencyKey): the spec says writes are idempotent when the header is supplied but defines no replay behavior. It is an Application concern (a store keyed by the header and route), not Domain.
- Upload rules (MIME allowlist, 50 MB limit) are Application request validation, not Domain (S:DOC-MimeAllowlist, S:DOC-MaxSize).
- Who sets the reserve transaction type: the spec's request body has the field, but the Add Reserve panel has no type control (S:API-POST-reserves, S:UI-Reserves). Working assumption: the request carries it and the frontend sends Add.
- The reserve request names the reserve instance by component id, not by kind (user decision, S:API-POST-reserves, A:API-PUT-reserve). Open: how a new instance is opened, since it has no id yet: the kind in the same request (exactly one of kind or component id) or a separate open step.
- Open item that touches Application: which warnings need acknowledgement (any unresolved warning can be acknowledged; only the policy-period warning blocks opening). Waiver roles, handler assignment, frozen claims and reserves on withdrawal are decided and recorded in ARCHITECTURE 'Decisions on gaps'.
- Unknown and removed child ids: a removed party or risk object is refused by the child's rule (PARTY_NOT_ACTIVE, RISK_OBJECT_REMOVED); an unknown id must be caught by the handler as not found before the aggregate method runs, because the claim step looks the child up with `Single`. Open: whether the two codes map to 404 or stay 422 (S:API-ErrorShape).

PROVISIONAL

- Creating a claim: the create handler calls `Claim.Create` (an empty Draft, its issues evaluated), then UpdateLossDetails, AddRiskObject and AddParty on it, and saves only after every call succeeded, in one unit of work (S:INTAKE-SingleCall). Consequence: creating a claim with parties raises PartyAddedEvent events besides ClaimCreatedEvent.
- Each public aggregate method gets an Application command and handler; claim inputs derive from ClaimBaseOperationInput (LossReference); an input carries Now and ActorId only when its step records a business time or a person's decision (create claim, remove risk object, waive, acknowledge, reserve submit and review), and the input builders stamp them. No controller or endpoint is written unless the spec documents one, so future services or APIs can use the commands without Domain changes.
- The loss reference is built for the claim's current policy, with the policy id in its PolicyPeriod (for LinkPolicy: the new policy; for a claim without a policy: PolicyPeriod.Empty); the Domain throws on a reference for another policy or without active cause codes, so a wrong load fails loudly instead of clearing decided issues.
- Decision inputs need a non-empty actor id and every posting move except cancel needs the Hangfire job id (the enqueue, the retry button and the job set it); the auto-approval needs no reviewer, the Domain leaves it empty.
- A status change goes through one Application command; the handler picks a runner (one input builder plus one transition) by target status, found by DI scanning, so there is no switch.
- Input builders are per input type, plain classes in Application behind a generic input-builder interface; there is no general builder, and builders are not MediatR requests. A builder that fills `Now` reads the clock once, so two calls run by one command get the same instant. Shared fact loaders (claim reserve facts, the loss reference) fetch their facts in one read through read-side repository interfaces. Every claim input needs the shared loss-reference loader; builders exist for the inputs with further outside facts: create claim, close, withdraw, send to payment, open and submit reserve, approve reserve and the limit override. Reject, retract and the posting moves are built from the request and the actor directly. Builders only load, map and stamp; rules stay in the Domain, and FluentValidation checks only the request shape.
- Only a request that cannot be bound at all (for example text where a date is expected) is rejected, at the API boundary, before any command runs.
- Errors: Application has an Error record (code, message, kind, optional field), the Result type, and one place that maps a Finding to an Error with kind validation (Critical findings fail the Result, Warning ones travel as warnings); not found, forbidden and conflict errors are created in Application only. The API maps kind to status (validation to 422, not found to 404, forbidden to 403, conflict to 409). Aggregate methods return an Outcome; Application maps it to Result.
- The valid next statuses for a not-permitted move (S:BR-ST-01) come from a catalog of all transitions, because a transition does not know the others; the not-permitted finding (`Transition.NotPermittedCode`) carries no list, so the catalog builds the message. Transitions expose no target or sources yet (removed 2026-10-16 as unused); the catalog design decides what they expose.
- Domain events are dispatched in two phases: handlers that write audit entries run before the commit, in the same transaction; handlers that enqueue the posting job run after the commit. A crash between commit and enqueue can lose the job; a sweep that re-enqueues old Pending postings is required (not optional), because close and withdraw refuse while an approved change is unposted, and an outbox is a later option. Fact definitions for close and withdraw: a pending change is PendingApproval; an unposted change is approved (Approved or AutoApproved) with posting Pending or Failed; an open balance is any reserve with approved balance above zero. Reserve submit and open take IsClaimEditable from the claim's state (claim.State.IsEditable) and the reserve fields from reserve.Reference. The posting retry (job and the retry button) calls ReserveChange.RetryPosting with the new job id before enqueueing; SetLimitOverride needs the claim approved total. HasApprovedReserve for send to payment means a reserve of a non-recoverable type with an approved balance above zero. Reopen, reject, approve, waive and the limit override take the actor's role from the authenticated user. The add-party validator requires a first or last name for a person and a company name for a company.
- Event envelope (parked 2026-10-16): Domain events carry business facts only. At save the Unit of Work pops events from every tracked entity (roots and children) and wraps each in an envelope: a new event id, the request time and the current user from the Application's clock and user service, plus the correlation id. Audit-log handlers and the outbox read the envelope, not the event.
- Open: `UserRole.From(kind)` already maps the role marker inside the Domain; decide whether the closed-set service below covers roles too or the handlers call `From`.
- Closed sets in Application: one generic closed-set class (marker and record types), which scans the Domain assembly for the concept's non-abstract records, creates one instance of each, keys them by the marker they declare, and throws on a missing or duplicate marker, plus one service behind a small interface that returns the right closed set for a concept. One extension method, AddDomainTypes, builds the whole set from a single list of concepts at registration and registers the service as a singleton, so startup fails there; one Application test calls the same extension so CI fails on a missing class. Users: Application handlers and input builders take the service by injection to turn a request enum into a record; the Persistence context takes it by constructor and uses it in the converters; the API does not use it (ASP.NET binds the enum natively); tests build the real one or use a fake of the interface. Failing at application start, not at compile time, is accepted.
- Infrastructure: the two Hangfire jobs, their startup registration and their audit writes live in Infrastructure and call the Domain posting steps (S:JOB-Registration). The request correlation id comes from the request context in Application when audit entries are written (S:AUD-Correlation).
- Claim number generation is an Application interface implemented in Persistence (see notes-layer-persistence.md).

- Every handler: load the aggregates, load the outside facts by query, build the input (time stamped once, actor and role from the authenticated user), call the aggregate method (it runs the step and its own follow-ups, see docs/ARCHITECTURE.md 'Aggregate follow-ups and events'), read the outcome, save in one Unit of Work, enqueue jobs and write audit entries after the commit. An expected refusal (auto-approve) is not an error.
