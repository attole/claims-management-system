OPEN

- Which roles may perform each status transition is decided later in the Application layer (user decision); the Domain only models roles (handler, supervisor, manager and an actor record) and keeps the rules the spec states explicitly (reopen needs a supervisor, approver authority covers the amount, setting the limit override needs a manager) (S:ROLE-Supervisor, S:ST-Open-UnderInvestigation).
- Idempotency-Key header on write operations (S:API-IdempotencyKey): the spec says writes are idempotent when the header is supplied but defines no replay behavior. It is an Application concern (a store keyed by the header and route), not Domain.
- Upload rules (MIME allowlist, 50 MB limit) are Application request validation, not Domain (S:DOC-MimeAllowlist, S:DOC-MaxSize).
- Who sets the reserve transaction type: the spec's request body has the field, but the Add Reserve panel has no type control (S:API-POST-reserves, S:UI-Reserves). Working assumption: the request carries it and the frontend sends Add.
- The reserve request names the reserve instance by component id, not by kind (user decision, S:API-POST-reserves, A:API-PUT-reserve). Open: how a new instance is opened, since it has no id yet: the kind in the same request (exactly one of kind or component id) or a separate open step.
- Open items that touch Application: which roles may waive a Critical issue (the Domain rule ISSUE_NOT_WAIVABLE only checks the issue); which warnings need acknowledgement; handler assignment; state-based permissions on Closed and Withdrawn claims (no operation checks the claim status today); what happens to pending reserves when a claim is withdrawn.
- An unknown or already removed party or risk object id is now a Domain rule finding (PARTY_NOT_ACTIVE, RISK_OBJECT_NOT_PRESENT), so it cannot become a 500. Open: whether Application maps these two codes to a not-found error (404) or leaves them as validation (422) (S:API-ErrorShape).

PROVISIONAL

- Creating a claim: the create handler runs CreateClaimOperation (which builds the empty Draft and evaluates its issues), then runs UpdateLossDetails, AddRiskObject and AddParty on it, and saves only after every operation succeeded, in one unit of work (S:INTAKE-SingleCall). Consequence: creating a claim with parties raises PartyAddedEvent events besides ClaimCreatedEvent.
- Each Domain operation gets an Application command and handler; the inputs derive from ClaimBaseOperationInput (Now and ActorId), which the input builders stamp. No controller or endpoint is written unless the spec documents one, so future services or APIs can use the commands without Domain changes.
- A status change goes through one Application command; the handler picks a runner (one input builder plus one transition) by target status, found by DI scanning, so there is no switch.
- Input builders are per input type, plain classes in Application behind a generic input-builder interface; there is no general builder. Builders are not MediatR requests. Every builder reads the clock once and stamps the operation time (Now on the input), so callers never set it; two operations run by one command must get the same instant. Shared snapshot loaders (claim reserve facts, reserve context, intake snapshot) fetch each snapshot in one read through read-side repository interfaces and are called by the builders. Outside data (for example reserve counts) is a nested snapshot record on the inputs that need it. An input with no outside data (open, investigate, revert, withdraw, reopen, reject, retract) is built directly from the request and the actor without a builder class; builders exist for create claim, pending payment, close, submit reserve and approve reserve. Builders only load and map and stamp the time; rules and decisions stay in the Domain. FluentValidation checks only the shape of the API request, and transition rules are not duplicated there.
- Only a request that cannot be bound at all (for example text where a date is expected) is rejected, at the API boundary, before any command runs.
- Errors: Application has an Error record (code, message, kind, optional field), the Result type, and one place that maps a DomainFinding to an Error with kind validation (blocking findings fail the Result, advisory ones travel as warnings); not found, forbidden and conflict errors are created in Application only. The API maps kind to status (validation to 422, not found to 404, forbidden to 403, conflict to 409). Domain operations return a FlowOutcome; Application maps it to Result.
- The Application layer fills the valid targets of a transition finding from the catalog of all transitions, because a transition does not know the other transitions.
- Domain events are dispatched in two phases: handlers that write audit entries run before the commit, in the same transaction; handlers that enqueue the posting job run after the commit. A crash between commit and enqueue can lose the job; a sweep that re-enqueues old Pending postings is the planned remedy, and an outbox is a later option.
- Closed sets in Application: one generic closed-set class (marker and record types), which scans the Domain assembly for the concept's non-abstract records, creates one instance of each, keys them by the marker they declare, and throws on a missing or duplicate marker, plus one service behind a small interface that returns the right closed set for a concept. One extension method, AddDomainTypes, builds the whole set from a single list of concepts at registration and registers the service as a singleton, so startup fails there; one Application test calls the same extension so CI fails on a missing class. Users: Application handlers and input builders take the service by injection to turn a request enum into a record; the Persistence context takes it by constructor and uses it in the converters; the API does not use it (ASP.NET binds the enum natively); tests build the real one or use a fake of the interface. Failing at application start, not at compile time, is accepted.
- Infrastructure: the two Hangfire jobs, their startup registration and their audit writes live in Infrastructure and call the Domain posting steps (S:JOB-Registration). The request correlation id comes from the request context in Application when audit entries are written (S:AUD-Correlation).
- Claim number generation is an Application interface implemented in Persistence (see notes-layer-persistence.md).

- Every handler: load the aggregates, build the snapshot by query, build the input (time stamped once, actor and role from the authenticated user), run the step, read the outcome, run the chains in docs/ARCHITECTURE.md 'Application chains', save in one Unit of Work, enqueue jobs and write audit entries after the commit. An expected refusal (auto-approve) is not an error.
