PROVISIONAL

- Each public aggregate method gets an Application command and handler. Claim inputs derive from ClaimBaseOperationInput (`PolicyPeriod` and `CauseCodes`); an input carries Now and ActorId only when its step records a business time or a person's decision (create claim, remove risk object or document, waive, acknowledge, history submit and decisions, document upload), and the input builders stamp them. No controller or endpoint is written unless the spec documents one.
- Reserve and document inputs take the claim's state: `claim.Reference` (`ClaimReference`) when a component or a document is created, `claim.State` for later steps. Load the claim by the component's or document's `ClaimId`.
- Decision inputs need a non-empty actor id and every posting move except cancel needs the Hangfire job id (the enqueue, the retry button and the job set it); the auto-approval needs no reviewer, the Domain leaves it empty.
- A claim state-changed handler closes the claim's reserve components when the claim becomes Closed or Withdrawn and reopens them when it is reopened, calling `Close` or `Reopen` on each in the same unit of work.
- Fact definitions: a pending row is PendingApproval; an unposted row is approved (Approved or AutoApproved) with posting Pending or Failed; an open balance is any component with approved balance above zero; HasApprovedReserve for send to payment is a component of a non-recoverable type with an approved balance above zero. The claim approved total is the net sum over all components. Reopen, reject, approve, waive and the limit override take the actor's role from the authenticated user.
- Only a request that cannot be bound at all (for example text where a date is expected) is rejected, at the API boundary, before any command runs.
- The valid next statuses for a not-permitted move (S:BR-ST-01) come from a catalog of all transitions, because a transition does not know the others; the not-permitted finding carries no list, so the catalog builds the message. Transitions expose no target or sources yet; the catalog design decides what they expose.
- Domain events are dispatched in two phases: handlers that write audit entries run before the commit, in the same transaction; handlers that enqueue the posting job run after the commit. A crash between the commit and the enqueue can lose the job; a sweep that re-enqueues old Pending postings is required (not optional), because close and withdraw refuse while an approved row is unposted, and an outbox is a later option. The posting retry (job and the retry button) calls `ReserveComponent.RetryHistoryPosting` with the new job id before enqueueing.
- Event context: Domain events carry business facts only. At save the Unit of Work pops events from every tracked entity, roots and children (the history rows raise their own events), and wraps each in an event context: a new event id, the request time and the current user from the Application's clock and user service, plus the correlation id. Audit-log handlers and the outbox read the event context, not the event.
- Policy and reference reads (no Domain change): policy search by number or client name and policy coverage read the seeded `Policies` table through a read interface; the cause-of-loss codes (the seeded `CauseOfLossCode` table, filtered by peril category for the list endpoint) and the claim-status catalog are reference reads; the claim-status catalog needs the transition catalog above.
- Documents: the Application builds the blob path (`claim-documents/{organisationId}/{claimId}/{sanitised filename}`), sanitises the filename, stores the bytes behind `IStorageService` (blob or local filesystem by setting), and returns a one-hour download URL; it passes the finished path and the file facts to `ClaimDocument.Upload`.
- Infrastructure: the two Hangfire jobs, their startup registration and their audit writes live in Infrastructure and call the Domain posting steps (S:JOB-Registration). The request correlation id comes from the request context in Application when audit entries are written (S:AUD-Correlation).
- Every handler: load the aggregates, load the outside facts by query, build the input (time stamped once, actor and role from the authenticated user), call the aggregate method (it runs the step and its own follow-ups, see docs/ARCHITECTURE.md 'Events'), read the outcome, save in one Unit of Work, enqueue jobs and write audit entries after the commit. An expected refusal (auto-approve) is not an error.

DECIDED

- Result: one `Result<T>` (success holds the value and the warnings, failure holds the errors and no value) plus a non-generic `Result` for commands that return nothing. `outcome.ToResult()` is the only conversion a handler calls; the finding-to-error step is private inside it, and the success check lives in one place.
- Error: an Application record (code, message, kind, optional field) with factories `Validation`, `NotFound`, `Forbidden` and `Conflict`; kinds map to 422, 404, 403 and 409. The spec fixes only the wire body (type, title, status and an `errors` object of field to messages, S:API-ErrorShape); the API builds it from the errors grouped by field and the code is not on the wire. `ValidationBehavior` returns a failed `Result` (validation errors with the property name as field), never throws, so every request returns `Result` or `Result<T>` and the API has one mapping path.
- Status rule: every finding is a 422; only the Application creates a 404, for an unknown id, which a repository `GetAsync` or reader reports before the aggregate method runs. A removed child (PARTY_NOT_ACTIVE, RISK_OBJECT_REMOVED, DOCUMENT_REMOVED) stays a 422.
- Fact readers are explicit and injected: `IClaimRepository` for the aggregate, `IPolicyReader` (the policy's `PolicyPeriod`; for LinkPolicy the new policy id), `ICauseCodeReader` (the active `CauseCodes`) and the reserve fact readers. There is no `ClaimContextLoader`. `IPolicyReader` and `ICauseCodeReader` also serve the policy search, coverage and cause-of-loss list reads of the seeded `Policies` and `CauseOfLossCodes` tables.
- Responses: a command returns `Result<TDto>` (or `Result`), never a Domain or HTTP type. A DTO of one flat entity is mapped with AutoMapper from the outcome's value; a DTO built from a `Move` or from several things is mapped by hand; values stamped on save (audit columns, `RowVer`) are mapped after the commit. A state change returns a small `ClaimStatusDto` (claim id, previous status, new status) built by hand from the `Move`. A command that must return the claim detail runs the detail query after the commit.
- Requests: every command implements `ICommand<TResponse>` and every query `IQuery<TResponse>` (Messaging folder), both constrained to `IFailableResult<TResponse>`, so a request that does not return a `Result` does not compile. A raw `IRequest<>` is not used. Add a test in pack 2 that every `ICommand<>` has a validator.
- Naming: event handlers run before the commit (`IBeforeCommitEventHandler`, audit writes, same transaction) or after it (`IAfterCommitEventHandler`, job enqueue); `EventContext` wraps a Domain event with its id, time, actor and correlation id (`ICorrelationContext`).
- Pack 2 layout: `Claims/Commands/` holds the claim-level use cases and `Claims/` holds `ClaimDto`, `ClaimMappingProfile`, the repository and number-generator interfaces and `ClaimErrors`; `Claims/Parties`, `Claims/RiskObjects`, `Claims/Loss` and `Claims/Issues` hold each child's use-case files (no folder per use case), DTO, request, validator, `ToDetails` extension and mapping profile. The test folders mirror it. State changes join as `Claims/StateChanges`; reserves and documents are their own aggregates with their own top-level folders.
- Pack 2 files: a use case is one file named after the command, holding the command record with its `ToInput` method (no extension class), its validator and its handler; its tests are one `<UseCase>CommandTests` class.
- Validation scope: validators check shape only: ids not empty, enums known, required strings not null, numbers the Domain would reject, and maximum lengths from the spec's column sizes (`ClaimFieldLengths`, reused by the Persistence column configuration). Text columns without a size (notes, descriptions, damage description) have no limit. Unknown ids are the handlers' 404, never a validator.
- Pack 2 shape: a handler loads the claim through `IClaimRepository.GetAsync` (a `Result<Claim>`, NotFound error from `ClaimErrors`), checks that a child id exists on the claim before the Domain call (the Domain `Single` throws on an unknown id), reads the policy period (`IPolicyReader.GetPeriodAsync`, `PolicyPeriod.Empty` for no policy) and the active cause codes, calls the aggregate through `command.ToInput(...)`, commits only on success and maps after the commit with `Result.Map`. Create claim builds the claim and every child in one lazy sequence that stops at the first refusal and stores only when all succeeded; the optional initial reserve joins it in pack 3. `ReportDate` is a field of the create command (the Domain input needs it apart from the received time); the limit override command is not built yet.
- Closed sets: each set has a typed one-line `From(kind)` in the Domain that calls one reflection helper (`Common/Markers/ClosedSet.cs`, variants found once and cached by marker); a Domain test loops over every enum value of all nine sets. Handlers, Persistence converters and input mapping call `From`; Application has no closed-set service.
- Create claim: one lazy sequence (policy link, loss, risk objects, parties) that stops at the first refusal; the claim is stored only after every step succeeded, with the warnings of every step on the result. Claim number generation is the Application interface `IClaimNumberGenerator`, implemented in Persistence. The policy period is read for the claim's current policy (`PolicyPeriod.Empty` for none; for LinkPolicy the new policy), the cause codes are the active codes, and the Domain throws on a wrong period or empty codes, so a wrong load fails loudly.
- Boundary text: a null in an optional text field becomes an empty string in `ToDetails`; required text is checked by the validators. Party names (a first or last name for a person, a company name for a company) are a request validator, not a Domain rule.
- Open point carried to pack 3b: the optional initial reserve on create claim. The limit override command is built (3a).
- Pack 3 decisions: whether liability is confirmed is a plain field on the status command; an upload never overwrites a stored blob with the same path (a duplicate name is a conflict, nothing is lost); the not-supported target (Draft) is an Application validation error with its own code, because the spec's not-permitted message belongs to the Domain transition only.
- Queries load no entity: Persistence projects straight into the DTO or a read model.
- Warnings travel on the `Result`; the state change response does not carry them, because they are stored issues readable from the claim detail.
- Reserve requests: the request carries the transaction type (Add, Adjust or Reverse) because the frontend knows the action; the validator only checks it is a known value. A new component is opened in the same request: exactly one of component type or component id; a type opens a new component (duplicate types per claim are allowed) and submits the first row in one unit of work, so a refusal stores nothing.
- Acknowledging warnings: the frontend shows the button on every warning and maps it to `Claim.AcknowledgeIssue`; the Domain does not change.
- Idempotency-Key: a filter or middleware in the API layer backed by a Persistence table with a unique index on key, tenant, user, method and route, plus a hash of the request body, an in-progress marker, the response status and body and the created time. The same key with a different body is a 422, a key still in progress is a 409, a completed key replays the stored response; rows expire after about 24 hours through a cleanup job; the completion write is in the same transaction as the command.
- Cause of loss is its own Domain folder (`CauseOfLoss/`: `CauseOfLossCode`, `PerilCategory`, `CauseCodes`), seeded like policies; Claims uses it the way it uses Policies.

PACKS

Four packs (user decision), each a stop point; the Hangfire jobs belong to Infrastructure and the EF mapping of the readers and repositories to Persistence, so Application tests use fakes for the readers.

- Pack 1 (built) - foundations: the Domain `ClosedSet` helper with the one-line `From` on all nine closed sets and its completeness test; `ErrorKind`, `Error`, `Result` (generic and non-generic) and `ToResult`; `IClock`, `ICurrentUser`, `IUnitOfWork`; the event context, the dispatch interfaces (before and after the commit) and the audit interface; tests that use real Domain outcomes.
- Pack 2 (built) - claim write use cases, the reference flow: the explicit readers (`IClaimRepository`, `IPolicyReader`, `ICauseCodeReader`); create claim, update loss details, add, update and remove party and risk object, link policy, assign handler, set severity, update notes, waive and acknowledge issue; commands, handlers, validators, DTOs and the mapping extensions.
- Pack 3 is split into three stop points. 3a (built) - state changes: the single `ChangeClaimStatusCommand`, a static dictionary in its handler from target status to the Domain call (no runner classes, no switch; a missing key is the unsupported-target error), `ClaimStatusContext` building the Domain inputs, `ClaimStatusDto` (previous status from the move, new status from the claim after the follow-ups, so a reopen reports Open), the reserve fact reader (`IClaimReserveReader`), the before-commit handler that closes and reopens the components, and the limit override command. 3b - reserves: submit (with a new component or an existing one, and the initial reserve on create claim), approve, reject, retract and the three posting moves, with the reserve component repository and the posting scheduler interface. 3c - documents: upload and remove behind `IStorageService`, the filename sanitiser and the blob path.
- Pack 4 - reads and idempotency: claim list and detail queries, policy search and coverage, the cause-of-loss list, the status list with the valid next statuses (derived from the transitions' own sources and targets, not a second table, so it needs the Domain to expose them), and the Idempotency-Key filter with its table contract.
- Pack 5 - events and audit: the audit-entry handler for every Domain event (the spec's event types), the event dispatcher and the Unit of Work that collect events from every tracked entity, wrap them in event contexts and run the handlers before and after the commit (loop until no new events); built with Persistence.
