PROVISIONAL

- Domain is built in packs: engine and base types (done), claim core (done), validation issues, lifecycle, reserves, and reference data and audit. Layer notes: notes-layer-application.md and notes-layer-persistence.md.
- Reserve side holds the component aggregate, the transaction history and the authority tiers (S:RES-Threshold-PerTransaction).
- Domain events: claim created, status changed, reserve submitted, approved, rejected, cancelled.
- The completeness issue rules (stored on the Draft): loss date missing, loss date in the future, description under 20 characters, cause code unknown or inactive (Critical); loss date outside the policy window, no policy linked, no risk objects (Warning); no claimant is also a Critical stored issue while a separate hard claimant rule on the transitions (and on closing) cannot be bypassed by a waiver (S:BR-C-01, S:BR-C-02, S:BR-C-05, S:BR-C-06, S:BR-C-07, S:BR-ST-02, S:CC-03). Not yet confirmed by the user.
- Removing a party is a claim operation with a rule that rejects removing the last active claimant (S:PARTY-LastClaimant); the claimant rules count active claimants only (assumption).
- The claim number is a Domain record that validates the format (S:BR-C-04); its generation, the Hangfire jobs and the correlation id belong to the Application, Persistence and Infrastructure notes.
- Pack 1 details: time reaches an operation inside its input (user decision, replacing the earlier TimeProvider argument and operation context): every input derives from OperationInput, which carries Now and refuses a default value; Application input builders read the clock once and stamp it, so callers never set it. Rules take only the subject and get time through the rule lambda; the apply step reads input.Now. The id helper takes that time (Ids.Next(now)), so no clock is read elsewhere in Domain, and tests build inputs with a fixed instant. Rules report warnings through a rule result holding an error list and a warning list, not a flag on the error (confirmed by the user); the operation aggregates the errors and warnings of all its rules into the outcome.
- The reserve transaction type (Add, Adjust, Reverse) is modeled as its own small type: an enum marker stored as text plus one policy record per type, found by the closed-set factory, like the reserve kinds. The documents give the three names and nothing else (no meaning, no rule, no link from a Reverse to the row it offsets, amount a signed delta whatever the type), and the names may change. Today each policy carries no behavior and no rule or calculation branches on the type. A future rule is added to that type's policy without touching Submit or the engine. The type is recorded on the transaction and required on the request. Renaming a type later means migrating the stored text.
- Reserve kinds are an enum marker with four small policy records (the only difference today is whether the balance may go negative), selected by the closed-set factory. Claim-wide reserve rules read a claim snapshot built by the input builder: policy linked, sum of the other components, override flag. At submit, exceeding 10 million produces a warning returned by the outcome type (which then carries a warnings list); at approve it blocks unless the claim's override flag is set. A claim operation requiring the manager role sets the flag, with an Application command and no controller. Whether the warning is also stored as a claim validation issue is not decided; returning it only is the working assumption.

DECISIONS

Where the spec and the assessment disagree, the spec is used. Each conflict is recorded here; the other side is not implemented.

- S:RES-Components over A:RES-Components: component names and negative rule follow the spec.
- S:BR-R-01 over A:BR-R-01: a reserve transaction amount is a signed delta that may be negative (a decrease). The rule is applied to the balance: a component's balance may not go negative, except the recoverable component (S:RES-Components "may go negative").
- S:RES-EventSourced over A:API-PUT-reserve: reserves are never updated; a change inserts a transaction.
- S:BR-R-05 over A:BR-R-07: over-limit handling follows the spec.
- S:BR-ST-01 over A:BR-C-06: the transition table in the spec is the state machine.
- S:JOB-SLA over A:JOB-SLA: the SLA job writes an audit entry and leaves the status unchanged; there is no extra status.
- S:DATA-Tenant over A:DATA-Tenant: the tenant column name follows the spec.
- S:BR-C-02 over A:BR-C-02: an out-of-period loss date warning must be cleared or acknowledged before opening.
- S:BR-C-03 over A:BR-C-03: a claimant is required before opening, not before saving the draft.
- S:ENT-Set over A:ENT-Set: the spec's entity set is the model.
- S:STATUS-Values (the status table, spec 4.1) is the source for claim statuses: Draft means created but incomplete or unvalidated, so a Draft may hold invalid and incomplete data and is saved with validation issues attached (S:VAL-Severity, S:BR-ST-02, S:CC-02). Statuses and their transitions are objects, not enums with if chains (see the lifecycle decisions below).
- The sample 422 body in spec 10.4 (S:API-ErrorShape) is illustrative only. It fixes the error shape (field name to list of messages), not which rules reject on create. The Draft table entry decides that.
- Critical means Critical: a missing loss date, a future loss date, a short description, and an unknown or inactive cause code are stored on the Draft as Critical issues, not rejected (S:V-LossDate-Required, S:BR-C-01, S:BR-C-07, S:BR-C-05). Warnings are stored as Warnings.
- Draft-tolerant schema (deviation from the spec's table, S:ENT-Set): the loss date has no value until set (an empty value in the domain, a nullable column) and the cause code is stored as text with no database foreign key. Draft -> Open requires a real date and an existing active code (S:BR-ST-02).
- A validation issue is a stored child of the Claim (our own design; the spec's entity list has none), with severity, message and a cleared, acknowledged or waived state.
- S:API-POST-reserve-approve over A:API-POST-reserve-decision: spec routes when the API pack is designed.

- Liability determined (S:ST-UnderInvestigation-PendingPayment) is an explicit confirmation passed with the status-change request, not stored on the claim. The move from UnderInvestigation to PendingPayment is blocked unless it is true; the move from Open has no such rule, as in the spec table. The confirmation is audit-logged with the status change. The spec defines no data for it, so the request body extends the spec's shape and the frontend needs a matching control.

- Withdrawal and reopen reasons (S:ST-Open-Withdrawn, S:BR-ST-04) are not fields on the claim. Every status change appends a row to a status-change history owned by the claim (our own entity, not in the spec): from, to, an optional reason record (a code and a text), who, and when. The history is append-only. The reason record is the field on the withdraw and reopen inputs. The claim's current reopen or withdrawal reason is read from the latest relevant history row, so nothing is set or cleared on the claim and no stale value can exist. Each change is also written to the audit log by the status-changed event.
- A reason is valid only when both its code and its text are provided (non-blank after trimming), for every withdrawal source and for reopen. One simple rule covers all three (S:ST-Open-Withdrawn, S:ST-UnderInvestigation-Withdrawn, S:ST-Closed-Reopened, S:BR-ST-04). This follows the domain need for a reportable code on every reason and is stricter than the spec, which asks for a code in some rows and only a reason in others; the user's domain call over the spec wording.

- The spec's closed date and closure reason columns on the claim (S:ENT-Set) are dropped (a deviation) and derived from the history too: the closed date is the time of the latest change into Closed and the closure reason is that row's reason, and both are empty unless the claim's current status is Closed. The spec's claims list rows and detail header show no closed date, so no list query needs it. Closing therefore sets nothing on the claim itself beyond the status; its optional reason travels on the history row.
- The closing justification note required when a claim closes with a nonzero reserve (S:CC-04) is recorded as an optional note on the closing history row, next to the closure reason; the spec names no field for it.
- The history records the Closed to Reopened change with its reason and the automatic Reopened to Open change without one, so a reopen produces two rows (see the Reopened decision below). The claim appends the history row inside its own status move, in the same transaction.

- Claim severity: modeled as its own type with an extra "unspecified" member (Domain holds no null), unset at creation, and nothing sets it yet because the spec gives no setter, default or rule (S:ENT-Set claim columns). It is named apart from the validation issue severity (Critical or Warning) to avoid confusing the two.
- Errors: the Domain has an abstract DomainError (code = rule ID, message) with subtypes only where extra data is needed: a rule violation with an optional field name (the transition blocker and the payload of a stored validation issue), and a transition-not-permitted error carrying from, to and the valid targets (S:BR-ST-01). The Application error record, the Result type and the status mapping are in notes-layer-application.md.

- Reopened is a normal state in the machine (S:ST-Closed-Reopened, S:ST-Reopened-Open, S:BR-ST-04): its own status value, its own state record, and a regular transition into it from Closed carrying the supervisor and reason rules. Reopened to Open is an ordinary From group on the Open transition with no rules today. The state names its automatic follow-up as a record (the Open state), and the claim moves on to it in the same operation, so a saved claim ends in Open. Two status-changed events are raised; the first hop is the reopen audit entry (Closed to Reopened with the reason). To change it later (a real resting state, or rules on the follow-up), remove the follow-up from the state or add rules to that From group; no other code changes.

Full Domain design agreements

- Domain methods that return a value and can fail return a small operation outcome type holding a value or a list of domain errors; Application maps it to its Result type. Rules and transitions keep returning lists.
- Any change to the claim's child data (party, document, reserve, status history) also touches the claim row, so its updated time and RowVer change. This makes the SLA job measure real activity and serializes reserve approvals on one claim, which removes the cross-component race on the claim-wide limit (S:BR-R-05, S:JOB-SLA).
- The posting idempotency key is the reserve component id plus the change sequence of the transaction (S:BR-R-06).
- The model is settable and updatable: the Domain has an operation for every claim field that can reasonably change (loss details, cause code, policy link, handler, severity, notes, issue acknowledgement and waiver), each re-evaluating the stored issues. The matching Application commands are in notes-layer-application.md.
- Rule messages use the spec's exact texts (user decision). CLAUDE.md now carries a narrow exception: those messages appear verbatim in Domain rule classes only (S:V-Messages), nowhere else.
- A reserve transaction row keeps its previous and new balance empty while pending; both are computed from the then-current approved balance when the row enters the ledger (immediately when auto-approved, at approval otherwise). The non-negative balance rule is checked at submission for early feedback and again at approval, so two pending decreases that each fit but together do not cannot both be approved (S:RES-History, S:BR-R-01). The change sequence is submission order, while balances follow approval order.
- No per-transaction approval cap: the manager tier approves any amount above the supervisor limit, and 10 million applies to the claim total with the manager override flag (S:BR-R-02, S:BR-R-05). The 10 million manager limit in the spec's roles table is read as loose wording and is not enforced.
- Reserve numbers update by recomputation: a component folds its own rows on every change and writes the result to its stored current amount, so the cached value cannot drift. The claim total is not stored; input builders sum the components' current amounts by query. Approving a pending row re-folds the approved rows, computes the effective previous balance, checks the non-negative rule, sets the row's balances, updates the cached amount, and raises the approved event.
- The Domain has one small engine that claims and reserves are built on: a rule interface over a subject, an operation (rules plus an apply step, all violations collected), a transition (an operation plus To and From status edges), the operation outcome type, and the domain error family. Claim transitions and edits, reserve submit, approve, reject, retract and the posting steps all use it; nothing else is framework.
- A claim can have many reserve components, including several of the same kind, mixed in any way; each is an instance with its own kind, transactions, change sequence, notes and status, and the claim total is the sum over all instances. Add always creates a new instance; Adjust and Reverse target an instance. The kind's policy applies to each instance. No unique index on a claim and a kind. The posting key's reserve id is the instance id (S:RES-Components, S:BR-R-06, A:API-PUT-reserve). Terms: reserve instance = ReserveComponent, its type = ReserveKind, a change = a ReserveHistory row ("transaction" is prose). No kind-specific extra data is modeled because the spec has none; the kind policy classes are the extension point.
- Approve, reject and retract act on a reserve transaction, not on the component, and run through the component as the aggregate root (the spec routes name a transaction id; the component is found from it). The subject of the approval and posting machines is the history row, which reaches its component for the balance fold. Other transactions are never changed by an action; a pending row that becomes invalid is caught by the re-check when it is acted on.
- The reserve approval and posting statuses use the engine's transition classes and, like every closed set, get a marker plus a record per value (superseding the earlier choice of markers only), because the record carries what the status changes: whether it counts toward the balance, whether it queues a posting job, whether it is pending.
- A closed set whose values carry data or behavior is a marker enum (the stored flag, text in the database) plus an abstract record and one sealed record per value: claim status, approval status, posting status, issue severity, issue state, user role, party role, party type, reserve kind and transaction type (kept as the extension point). Pure labels stay plain enums, stored as text with EF's built-in conversion and bound natively by ASP.NET: claim severity (with an unspecified member instead of null), asset type, peril category, policy status and component status. A plain enum is promoted later by adding it to the concept list and writing its records; the stored values do not change. An if on a plain enum value inside a rule is the signal to promote it. The document type and the audit event type stay open (plain text record and named constants) because the spec lists them as examples. The Domain holds only these types: no registry, no reflection, no conversion. Edges and follow-ups name record types. Domain also holds one tiny shared abstract record, Marked of the marker enum, that carries the marker; every concept's abstract record derives from it. Records must be creatable without arguments and carry any data as constants. Not in the system: document type, audit event type, authority tiers, transitions. The EF converters and the registry service are described in notes-layer-persistence.md and notes-layer-application.md.
- The engine runs on the component for Submit (an Operation) and on the transaction for approve, reject, retract and the posting steps (Transitions). Rules are declared on the operation or transition with Require and read the subject's own data (the component's rows and kind policy) or the snapshot in the input; the builder carries only data from outside the aggregate.
- The reserve change entity is named after its table, ReserveHistory (one append-only row per change; "transaction" is prose in the spec and the route id is a history row id). Its approval status approves that one change, not the component or the claim. The request amount is the signed delta, typed by the user as the stored value, with no client-side calculation; a component's balance may not go below zero (the recoverable kind may). A component's balance is the sum of its Approved and AutoApproved deltas and equals the new balance of its last approved row; the sum is the source of truth and an invariant checks the stored snapshot against it. The spec's wording "posted/approved" for the current amount is read as approval status, not posting status (S:BR-R-01, S:RES-History, S:RES-EventSourced).
- A policy period is a domain record of two calendar dates (date-only, not date-time) with both ends inclusive, and a method that answers whether a loss date falls inside it by taking the calendar date of the loss date in its own offset. Both ends inclusive follows the spec's seed periods (for example 1 June to 31 May two years later) and sits apart from real policies, which usually run to 12:01 a.m. at the insured's address (S:BR-C-02, S:POL-Seed).
- A policy has an optional cancellation effective date (a new nullable column on the simulated policy table, a deviation; the domain holds an empty value when absent). The coverage window is the start up to the earlier of the end date and the cancellation date, and the loss-date check uses that window, so a loss after cancellation raises the existing policy-period warning (S:BR-C-02). The policy status (Active, Expired, Cancelled) is informational: no rule reads the stored value, and Expired changes nothing because only the loss date against the window matters. The status can be derived as of a date: cancelled when a cancellation date is set, expired when the date is past the end, active otherwise.
- The estimated loss amount is optional, as the spec column is nullable (user decision): EstimatedLossAmount is a sealed record with an Empty instance and an IsSet flag, so no estimate differs from an estimate of 0. No non-negative check exists because the documents state no bound (user decision: an unsourced check was dropped). It is not linked to reserves or severity, and no stored issue is raised for it because the spec has no rule for it.
- The claim's reported date (when notice was received) and the loss event's report date (when formally reported) are not user-entered; both are set by the system at creation from the current time passed into the creation method (not a database default and not the client), and can be changed later by a domain operation. The loss date is client-supplied. The audit created-at is a separate value set by the save interceptor.
- The risk object primary flag is a plain flag with no uniqueness rule, default false, and no behavior; it is settable by a domain operation. The spec has only the column, the intake form has no control for it, and no claims-system documentation found enforces a single primary.
- A reserve component's Active or Closed status is informational: Active by default, nothing excludes a Closed component from any total and nothing blocks transactions, until the spec defines it. A domain operation can flip it (S:RES-Components).
- An initial reserve submitted with no policy linked rejects the whole create with a 422 and saves nothing (S:BR-C-06, S:INTAKE-SingleCall). The frontend should disable the reserve section while the policy is unknown. Once a policy is linked later, a reserve goes through the normal reserve command.

Domain building blocks

- Base types: an entity base (Id, equality by Id, a private list of domain events), an aggregate root base (adds RowVer, a byte array initialised empty, set by the database as a concurrency token), and a plain domain event type. No MediatR in Domain; the Unit of Work dispatches events through an Application interface.
- Ids are generated in the domain by a small helper that produces SQL Server-ordered sequential GUIDs, so aggregates and their events have ids at creation and tests need no database. No database default.
- No value-object base class. Value-like types (claim number, money, policy period, empty loss date) are plain records.
- No smart enums. Auditing, soft delete and tenant fields are interfaces on the entities that need them, set by a save interceptor in Persistence; append-only rows implement only what applies (S:DATA-AuditColumns, S:DATA-SoftDelete, S:DATA-Tenant).
- Domain methods take the current time as a parameter; no static clock in Domain.
- Roles are modeled in the Domain as a role marker (handler, supervisor, manager) and an actor record (user id and role). The authority tiers and the rules the spec states explicitly use them. Which roles may call which operation is an Application concern.
- Rule failures are domain errors carrying the rule id as code (see the errors decision above).

Claim lifecycle

- A status enum is only a marker and the stored key (text in the database). Each status has a small state record declaring which enum value it is. The Domain holds no registry and no conversion; see the marker-and-record decision under the full Domain design agreements.
- Each transition is a class named for its target, generic over its own input record. Edges are declared with a fluent builder: To and From naming state record types, and Require(rule), with Require taking either a ready rule or a lambda that builds the rule from the input. A From group lists sources that share rules, and a target reachable from sources with different rules uses one From group per source (for example PendingPayment from Open versus from UnderInvestigation).
- Storage inside a transition is a dictionary from source status to its rule factories; a source listed in two groups throws when the transition is built. The valid next statuses are derived from all transitions and feed both the invalid-move message and the statuses endpoint (S:BR-ST-01, S:API-GET-statuses).
- Rules are plain classes behind one interface that checks a subject (the claim, a component or a transaction) and returns domain errors; their data comes through the constructor. All rules of a group are evaluated and every blocker is returned (S:BR-ST-03).
- Input is a plain record per operation or transition that derives from OperationInput, a small base that carries Now (the operation time) and refuses a default value. There are no capability interfaces; the engine does not read the input beyond that base. An actor field appears only on inputs whose rules or events read it.
- The claim's state setter is internal to Domain, so only transitions can change status. A transition's apply step makes the claim's own changes; the closed date and reasons are no longer fields (they are derived from the history), so the status move appends the history row and the claim raises the status-changed event once. Effects on other things (audit entry, posting jobs) react to events: audit in the same transaction, jobs after commit.
- Per-transition tests check sources and rule IDs against the spec table, and a test checks that every input has a transition.

Reserves

- A component owns an append-only list of transactions and its balance is the sum of approved ones. A transaction has its own small state machine of the same shape, driven by rules such as no self-approval, approver authority covering the amount, and a rejection reason; posting status is a second small machine driven by the job.
- Authority tiers are objects behind one abstraction, chosen by the single transaction amount (S:RES-Threshold-PerTransaction). A domain service takes the claim-wide total as input for the limit warning.
- The engine is shared from the start (see the full Domain design agreements); the reserve machines are built on it, not copied from the claim's.
