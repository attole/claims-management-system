# Infrastructure layer

Rules and contracts of Infrastructure: the background jobs and the adapters for outside services. It implements `IStorageService` and `IPostingScheduler` and sends the job commands (`docs/layers/application.md` 'Provides and expects'). `.claude/CLAUDE.md` holds the short rules and points here; read this file before changing the Infrastructure project or reviewing its code. Status: complete, with tests (this file holds what the Domain and the Application hand over).

## Layout

- The project holds the Hangfire job definitions and their registration, and the adapters that implement ports the Application defines (`IStorageService`, `IPostingScheduler`, and email if it is added). `InfrastructureServiceExtensions` registers them; settings are options classes bound with `BindConfiguration`.
- `BackgroundJobs/` holds the Hangfire host (storage, server, dashboard and its options), the on-demand posting job with its scheduler, and the shared `JobResult`. `BackgroundJobs/Recurring/` holds the scheduled jobs, their options and `RecurringJobsServiceExtensions` (`AddRecurringJobs` registers options and job classes, `UseRecurringJobs` adds the recurring definitions at startup); a new scheduled job goes there.
- A job or adapter holds no business logic. It sends a command through MediatR or calls a port, and nothing else.

## Jobs

- **Posting job (GL).** The Application enqueues it after the commit through `IPostingScheduler` (an approved or auto-approved row, or a failed posting returned to pending). The job marks the row through `MarkReservePostedCommand` or `MarkReservePostingFailedCommand`.
  - An approval passes an empty job id; the job assigns its own and reports it when it marks the row. A retry stores a fresh token as the job id (the Domain requires one on the move) and the after-commit handler passes it to the scheduler, so the job runs under the recorded id.
  - The job is idempotent (S:JOB-GL-Idempotent): marking an already posted row succeeds without a write. It retries automatically and, when the retries are exhausted, marks the row failed (S:JOB-GL-Failure).
  - `HangfirePostingScheduler` implements `IPostingScheduler` and enqueues `ReservePostingJob`. A refused command counts as a failure, so it retries like an exception. `ReservePostingJob.MaxRetries` is 3 (four runs); the run with the retry count at the maximum marks the row failed instead of throwing.
  - **Tenancy.** A job has no user, so the scheduler carries the organisation of the row as a job argument (`IPostingScheduler.EnqueueAsync` takes it first; the after-commit handlers read it from `ICurrentUser`, the sweep from `UnpostedReserve.OrganisationId`). The job sets it on the `ScopedCurrentUser` (system actor `Guid.Empty`, lowest role) of a fresh DI scope and sends the command there, so the repositories and the tenant filter stay in force on the write path. Each command gets its own scope: after a failed commit the first scope's context still tracks the unsaved change, and the failed-mark would load that stale row.
  - `ScopedCurrentUser` is the one scoped `ICurrentUser` that Infrastructure registers (`IdentityServiceExtensions`). The API sets it from the token at the start of a request; a job sets it from its arguments.
  - The audit entries for posted and failed come from the posting events, not from the job.
- **SLA job.** Runs every 15 minutes by default (S:JOB-SLA; `SlaBreachOptions`, `Hangfire:SlaBreach:IntervalMinutes`, a divisor of 60, validated at startup, so a deployment can change the cadence the rule names) and sends `DetectSlaBreachesCommand`. The command writes the breach entries as the system actor and respects the 24-hour dedupe; the job writes nothing itself. `SlaBreachJob` does not retry (`Attempts = 0`): the next run is the retry. It runs without a user; the SLA reader spans organisations and the audit service takes the organisation from the claim.
- **Posting sweep.** `PostingSweepJob` sends `ResendStalePostingsCommand` with a minimum age taken from `PostingSweepOptions`. Both of its settings are validated at startup: `Hangfire:PostingSweep:MinimumAge` (default 10 minutes, positive) and `Hangfire:PostingSweep:IntervalMinutes` (default 5, a divisor of 60: the cron minute step restarts every hour, so any other value gives uneven gaps). It does not retry. It is required: a crash between the commit and the enqueue loses the posting job, and close and withdraw refuse while an approved row is unposted.
- **Idempotency cleanup.** `IdempotencyCleanupJob` sends `PurgeExpiredIdempotencyKeysCommand`, which deletes the stored Idempotency-Key rows older than 24 hours, the same window the store uses to treat a key as new. `Hangfire:IdempotencyCleanup:IntervalHours` (default 1; 1, 2, 3, 4, 6, 8 or 12). It does not retry.
- **Blob sweep.** `BlobSweepJob` sends `SweepOrphanBlobsCommand` with a minimum age from `BlobSweepOptions`. It lists the document blobs last written before that age, asks Persistence which paths a document row refers to (soft-deleted rows and every organisation count as referenced) and deletes each unreferenced blob, checking references 500 paths at a time. The minimum age (`Hangfire:BlobSweep:MinimumAge`, default 1 day) protects a blob stored before its commit. The sweep is destructive, so it is a feature switch that defaults to off (`Hangfire:BlobSweep:Enabled`); while it is off the startup registration removes the recurring definition. `IntervalHours` defaults to 12. It does not retry. Run it against Azurite or a real account before turning it on: the Azure listing and delete were not run against a real account.
- **Registration.** All recurring jobs are registered at application startup (S:JOB-Registration): `UseInfrastructure` calls `UseRecurringJobs`, which adds or updates each job by a fixed id (`sla-breach-detection`, `posting-sweep`, `idempotency-cleanup` and `blob-sweep`; the blob sweep is added only while its switch is on, otherwise its definition is removed). A job that refuses its command throws (`JobResult.ThrowIfFailed`), so the failure shows in the dashboard. The Hangfire dashboard is behind its feature switch, which defaults to off.
- Every job is safe to run twice.

## Clock

- `SystemClock` implements `IClock` (singleton). The Persistence interceptors, the stores and the handlers read time only through it.

## Current user

- `ScopedCurrentUser` implements `ICurrentUser` as a settable scoped holder (`Set(id, organisationId, role)`) and is the registered `ICurrentUser`. Its empty state (empty ids, lowest role) is what the tenant filter sees when nothing set it.

## Storage adapter

- `IStorageService` stores a blob and returns a download URL. The URL is made on read with a one-hour lifetime (S:BR-D-02). Removing a document is a soft delete and keeps its blob; only the blob sweep deletes, and only a blob no document row refers to. `ListAsync(container, createdBefore)` returns the full paths (`<container>/<name>`) of the blobs last written before the time, and `DeleteAsync(path)` removes one and ignores a missing blob.
- The blob path is built by the Application (`claim-documents/{organisationId}/{claimId}/{uploadId}_{sanitised file name}`); the adapter only stores under it. The first segment is the container; the rest is the blob name.
- The provider is `StorageProvider`, `LocalFileSystem` (default) or `AzureBlob` (S:BR-D-03). `StorageOptionsValidator` stops the app at startup naming each missing key: `AzureConnectionString` for Azure, `LocalBaseUrl` and `LocalSigningKey` for the local provider.
- **Azure.** `AzureBlobStorageService` creates the container when missing, uploads with the content type and returns a read-only SAS URL that carries the original file name as a content disposition, so the browser saves the file without the upload id prefix. The SAS is signed with the account key, so the connection string must carry one. Not run against a real account or Azurite; the tests cover the URL shape and its expiry only.
- **Local.** `LocalFileSystemStorageService` writes under `LocalRoot` (default `uploads`, the container segment dropped, so `uploads/{organisationId}/{claimId}/...`). A path that leaves the root is refused. The URL is `Storage:LocalBaseUrl` + `LocalDownloadToken.DownloadRoute` + a token. The token is the expiry and the path signed with HMAC-SHA256 under `Storage:LocalSigningKey` (a secret, user-secrets); `LocalDownloadToken.ReadPath` returns the path, or an empty string when the token is malformed, tampered with or expired.
- `LocalDocumentDownloads` implements the Application port `ILocalDocumentDownloads`: it checks the provider and the token, finds the file and names it, and the API streams the result. This is the one place bytes pass through the API, a local-only exception to S:BR-D-02 (the Azure URL goes straight to the blob).
- A failed commit after the blob is stored leaves an unreferenced blob; the blob sweep (the Jobs section above) removes those.
