# Persistence layer

Rules and contracts of Persistence: schema conventions, how the Domain is mapped, the save interceptor, the Unit of Work, readers and repositories, and migrations. It implements the ports the Application defines (`docs/layers/application.md` 'Provides and expects'). `.claude/CLAUDE.md` holds the short rules and points here; read this file before changing the Persistence project or reviewing its code. The schema departures from the specification and their reasons are in `docs/ARCHITECTURE.md` 'Schema departures from the spec'.

Status: built and tested: the context, the model-wide conventions (including `RowVer`), the filters, the converters, the save interceptor with the root touch, every entity mapping (claim and its children, policy, cause of loss, reserves, documents), the claim, reserve and document repositories, the claim, policy, cause-code, reserve and document readers, the audit log service and reader, the claim number generator, the idempotency store, the SLA reader, the Unit of Work, the migrations with the seed and the claim list view, and the design-time factory. The SQL Server test set (`ClaimsModule.Persistence.SqlServerTests`) checks the SQL against LocalDB. Points marked (spiked) were checked in a throwaway EF Core 9 spike outside the repo (SQL Server provider for the model and script, SQLite in memory for round trips; the test context maps every `DateTimeOffset` to a binary value so SQLite can compare and order them, except on the claim list view, which keeps the stored text, so the loss-date filter of the claim list is untestable on SQLite and not yet covered in the SQL Server set); points marked (not verified) need a real-database check when they are written. Open questions are in `.claude/temp/notes-parking-lot.md`.

## Layout

- One `IEntityTypeConfiguration<T>` per entity, with the Fluent API only and no data annotations. Converters, repositories, readers, interceptors and migrations have their own folders; `PersistenceServiceExtensions` registers them. A standalone infrastructure feature with its own table and no Domain aggregate (the audit log, the claim number counter, later the idempotency store) has one feature folder holding its row, configuration, service and reader (`Audit/`, `ClaimNumbers/`), with its tests in the mirrored folder; the interceptors stay in `Interceptors/` because they serve every table.
- Interfaces that Persistence implements are defined in the Application (repositories, readers, `IUnitOfWork`, the claim number generator, the audit service and reader, the idempotency store). The Domain is never referenced for a Persistence concern.
- Test folders mirror source folders; round trips use SQLite in memory. `ClaimsModule.Persistence.SqlServerTests` is the SQL Server test set: each run migrates a fresh database on LocalDB (or the server in `CLAIMS_TEST_SQLSERVER`), drops it afterwards, and skips every test when no server answers. It checks the migrations against the model, the seed, the claim list view, the audit grant (as a user in the `claims_app` role), the claim number SQL, the duplicate-key translation and the `RowVer` conflict.

## Schema conventions

- Primary keys are sequential GUIDs generated in the Domain (`Ids.Next()`); Persistence also declares the `NEWSEQUENTIALID()` default so the schema matches the specification.
- A column the Application validates takes its length from the Application's field-length constants (`DocumentFieldLengths`, `ReserveFieldLengths`, `ClaimFieldLengths`), never a second literal; when the constant is missing it is added to the Application first, with the validator rule, and then used here, so a valid request cannot overflow its column. A column with no validator keeps its own length.
- Money is `DECIMAL(19,4)` (`HasPrecision(19, 4)`), timestamps are `DATETIMEOFFSET(7)` in UTC, short codes `NVARCHAR(50)`.
- Table names are the specification's section 9: `Claims`, `LossEvents`, `ClaimParties`, `ClaimRiskObjects`, `ClaimReserveComponents`, `ReserveHistory`, `ClaimDocuments`, `ClaimAuditLog`, `CauseOfLossCodes`, `Policies`. Entity classes keep their Domain names and map with `ToTable` (`ReserveComponent` to `ClaimReserveComponents` with its state column named `Status`, and so on). Columns are PascalCase. Tables the specification does not list are named here: `ClaimIssues`, `ClaimStateChanges`, `PolicyCoverageTypes`, `ClaimNumberCounters` and `IdempotencyKeys`.
- Every business table has soft delete (`IsDeleted`, `DeletedAt`), audit columns and a tenant column, with global query filters for soft delete and tenant. A table soft-deletes exactly when its entity implements `ISoftDeletable`; the others (state-change history, reserve history) keep their rows, and a `Remove` on one of them throws. The audit log and the claim state changes are append-only (`IAppendOnly`: any change or remove throws; the reserve history is not marked, because approval and posting update its row); a removed party is deactivated (`IsActive`) instead.
- Aggregate roots (the claim, the reserve component, the document) carry a `RowVer` concurrency token.
- A Draft claim may be incomplete: the loss date column is nullable and the cause code has no foreign key (see `docs/ARCHITECTURE.md` 'Schema departures from the spec').
- The audit log has no update or delete permission in the application, and an index by claim and event type for the SLA dedupe lookup. `AuditLogService` takes the organisation from the claim (the tracked claim, else a lookup that ignores the filters), not from the current user, because a job has no organisation; it only adds a row to the context (the Unit of Work saves it with the command); the interceptor stamps `CreatedAt` and `UserCreated` (the spec's time and user columns, null for the system actor) and throws on a changed or removed audit row. The relationship to the claim does not mark the root modified: an audit row must not move the claim's `UpdatedAt`, which the SLA job reads. The reader pages newest first, by `CreatedAt` descending and then `Id` descending for entries at the same instant.
- One `ClaimsDbContext` serves every repository, reader and service, so one save covers a command. A model-wide convention adds the audit shadow columns, the soft-delete columns (for `ISoftDeletable` entities only) and the key default to every `Entity`. The query filters come from two base classes: a configuration derives from `TenantConfiguration<T>` (any `ITenantOwned` type, so the claim number counter and the list read model too), or from `SoftDeleteConfiguration<T>` when its entity is soft-deletable, and its `Configure` override starts with `base.Configure(builder)`, which applies the filter (a test fails when an entity has no filter, so a forgotten call is caught). A configuration takes the `ClaimsDbContext` in its constructor, so `ClaimsDbContext.ApplyConfigurations` registers each one by hand; a test fails when a configuration is not applied or an entity has no filter. The filter must read `CurrentOrganisationId` through the context (spiked: EF re-binds it per context instance), never a Guid value taken at model build, which the cached model would freeze for every later request.
- The tenant filter reads the organisation of `ICurrentUser`. The posting job runs under the organisation of its row, so the filter stays in force on its writes (`docs/layers/infrastructure.md` 'Posting job'). Any other job has no user: the filter must see an empty organisation and not throw, and job readers bypass it on purpose (`IgnoreQueryFilters` with the soft-delete test written out).
- The coverage types of a policy are a child table (`PolicyCoverageTypes`, one row per type), not a JSON column.
- `CauseOfLossCodes` carries a `SortOrder` shadow column for the display order; the Domain has no order.

## Mapping the Domain

- **Details values** (`LossDetails`, `PartyDetails`, `RiskObjectDetails`, `ReserveHistoryDetails`, `ClaimDocumentDetails`, `Policy.Period`) are complex properties in the entity's table, replaced as a whole (spiked: only the changed members are marked modified). Give every member `HasColumnName` to match the specification, because the default carries a `Details_` prefix. EF binds a record's constructor to mapped members (checked), so a value with a member that has no column of its own (`PolicyPeriod.PolicyId`) is not mapped as a complex property.
- **Policy** maps its dates as scalar shadow columns (`EffectiveDate`, `ExpirationDate` and a nullable `CancelledDate`) and ignores `Period` and `CoverageTypes`; no repository loads a Policy. The policy reader builds `PolicyPeriod` from the row and its id (a NULL cancellation date becomes `DateOnly.MinValue`) and fills the status from `PolicyPeriod.StatusOn(today)` with the date of `IClock` (the rule lives only in the Domain); the specification's status column is not stored (`docs/ARCHITECTURE.md` 'Schema departures from the spec').
- **Entities** have a private parameterless constructor with empty placeholders, because EF cannot bind domain constructors that take values it does not map; `EntityConstructionTests` builds each through it.
- **Absent values** are sealed records with an `Empty` instance (`LossDate`, `EstimatedLossAmount`), since EF refuses a nullable column on a non-nullable struct. The converter maps NULL to `Empty` and `Empty` to NULL (`ConvertsNulls`) and the property is declared optional (spiked for the loss date). A value-type member cannot be optional (checked), so a column that must be NULL for a Domain value type is a Persistence shadow column, and the reader maps NULL to the empty value. A stored zero estimate must read back as a set estimate, because no estimate is not an estimate of 0 (user decision; not verified).
- **Closed sets** use one generic converter (marker text out, record in) that takes the set's public `From`; plain enums use EF's text conversion. The stored text is the enum member name, so renaming a member breaks the stored rows; an unknown text throws on read, which is the intended loud failure, and a test pins the stored names of each set when it is mapped. A converter maps one value and never an entity or a DTO (AutoMapper stays in the Application for DTOs). A converter is a subclass of `ValueConverter` (the only way to set `ConvertsNulls`) whose two conversions are named `private static readonly Expression<Func<...>>` fields, `_toColumn` and `_fromColumn`, passed to the base constructor (EF needs expressions, not delegates); a converter that needs an argument builds the second expression in a private static method. A closed set inside details (party role and type) is a converted scalar with a maximum length. No design-time factory unless migrations cannot create the context.
- **Issues:** `ClaimValidationIssue` is a child collection of the claim with the finding as a complex property (code, field, message, evidence and the severity as a scalar; the evidence column is as large as the trimmed loss description), the state as a converted scalar, and a resolved time and resolver with empty defaults. Cleared issues stay as history.
- **History rows:** a child table of the component with a foreign key (`ReserveComponentId`), the denormalised claim id, and the component type and `SubmittedAt` as mapped columns. The balances, the review and the posting details are complex properties with empty defaults, never NULL (an unset review stores the empty values, and `HasBalances` stores `IsSet`). Rows are append-only. The idempotency key is computed by the row and not stored; a second submit on the same component conflicts through the component's `RowVer`, which the root touch moves.
- EF 9 cannot index a member of a complex property (checked), so the history table has no index on its claim id or change sequence. Every other nullable column gets the same check as the loss date before it is mapped.
- **Closed sets in queries:** compare a converted column against a local variable holding the instance (or an array of them); a `static` field is inlined as a constant and does not translate (checked). `DateTimeOffset` comparisons do not translate on SQLite, so the stale-posting reader filters the age after projecting the few pending rows.

## Save interceptor

- The save work is four interceptors, each with one job, built by `SaveInterceptors.Create` in the order they depend on: `RootTouchInterceptor` (runs `DetectChanges` once, then flags the roots), `AppendOnlyInterceptor` (rejects a change to an `IAppendOnly` row), `SoftDeleteInterceptor` (turns a remove into the flag and stamps `DeletedAt`; refuses a remove on a row that is not soft-deletable) and `RowStampInterceptor` (stamps created and modified, so it sees the rows the earlier steps changed). EF runs interceptors in registration order, so the order lives in that one factory and a test pins it; a new step is added there. Each derives from `SaveStepInterceptor`, which skips a save with no context and handles the sync and async hooks. `DeletedAt` and `UpdatedAt` of a soft-deleted row come from two clock reads, so they can differ by microseconds with a real clock.
- `CreatedAt`, `UpdatedAt`, `UserCreated`, `UserModified` and `DeletedAt` are EF shadow properties, not Domain properties (user decision). `DeletedAt` is stamped when a row's `IsDeleted` turns true, whether the Domain flipped it or a remove was turned into a soft delete. The interceptor stamps them: an added row sets `CreatedAt` and `UserCreated`, a modified row sets `UpdatedAt` and `UserModified`, with the time and user from the Application's clock and current-user interfaces, the same source the input builders stamp from.
- The Domain sets only business fields: `OrganisationId` (on the base `Entity`, `ITenantOwned`) and the soft-delete flag (`ISoftDeletable.IsDeleted`) for a removed risk object or document.
- **Root touch:** a relationship whose rows must bump a root is declared in its configuration with `.MarksRootModified()` (a Persistence annotation on the foreign key, so the Domain stays unaware; a test fails when a foreign key to a root is not marked, and a reference that must not bump a root would be listed there as an exception). When a row is added, modified or soft-deleted, the interceptor marks the roots its marked foreign keys point to as modified (`UpdatedAt` is flagged, then stamped like any modified row), so the root's `UpdatedAt` and `RowVer` move. The touch repeats up the chain, so a history write moves its component and then the claim row, which serializes concurrent approvals across a claim's components; the SLA job depends on the claim touch. A root that is not tracked in the context is not touched. `RowVer` is a rowversion on SQL Server and a plain concurrency token (never regenerated) on SQLite, so a conflict test needs SQL Server.
- The global soft-delete filter reads the flag through the interface property; a hard `Remove` on a tracked `ISoftDeletable` entity becomes the soft-delete flag in the interceptor.
- The interceptor reaches the current user and the time through Application interfaces and uses member names as strings, so a test against a real context must cover every interface member.

## Unit of Work and events

One `UnitOfWork` class implements `IUnitOfWork` over the `DbContext`:

1. Pop the events of every tracked entity, roots and children (`ChangeTracker.Entries<Entity>()`).
2. Wrap each in an `ExtendedEvent` (new `Ids.Next()`, clock time, current user id, correlation id).
3. Run the before-commit handlers; they can raise more events, so repeat until no new event appears.
4. Save once.
5. Run the after-commit handlers.

Tests against EF cover the order (before, save, after), the repeat until empty (capped at 10 passes, past which it throws so a cycle between handlers fails instead of hanging), the context fields, and no save when a before-commit handler throws. Idempotency completion is its own save, not part of the command transaction.

**Save errors:** the Unit of Work catches `DbUpdateConcurrencyException` and a unique-index `DbUpdateException` and throws the Application's `ConcurrencyConflictException`, so the Application never sees an EF type. The API's exception handler maps it to 409 (`docs/layers/api.md` 'Errors'). Nothing else is caught. The unique-index test reads the SQL Server error numbers 2601 and 2627, so the duplicate-key translation runs only in the SQL Server test set; the concurrency translation is tested on SQLite through a row removed by another writer, because `RowVer` does not change there, and on SQL Server through a real `RowVer` change.

## Readers and repositories

- A repository `GetAsync` returns `Result<T>` with the not-found error, scoped by claim id so a wrong claim is a not found.
- The reserve and document readers load the claim's rows without tracking and use the Domain members (`ApprovedBalance`, `IsApproved`) and the Application's mapping profiles, so the balance and approval rules stay in the Domain; a claim has few components and rows. Set-based readers across claims (the job readers) query in SQL. `IClaimDocumentReader.FindReferencedPathsAsync` returns which of the given blob paths a document row refers to, soft-deleted rows and every organisation included (it ignores the query filters), for the orphan blob sweep.
- Other readers project straight into DTOs and load no entity (the cause-code reader uses `ProjectTo` with the Application profile). The claim detail reader is the exception with the reserve and document readers: it loads the claim with its children untracked and maps through the profiles, because it reads Domain members such as the issue `IsCurrent` rule. Computed members (`IsSet`, `IsClaimant`), the marker of a converted closed set and range comparisons on converted values do not translate to SQL; equality against an instance and `OrderBy` do. List and search queries therefore project to DTOs or use flat read models mapped to the same table with plain nullable columns, and never filter a Domain entity with `AsEnumerable`.
- Reader facts: a pending row is `PendingApproval`; an unposted row is approved (Approved or AutoApproved) with posting Pending or Failed; an open balance is a component with an approved balance above zero; an approved reserve for payment is any transaction of the claim that is Approved or AutoApproved; the claim approved total is the net sum over all components.
- The job readers: `ISlaClaimReader` lists Draft or Open claims not updated for 48 hours with no breach entry in the last 24 hours (it ignores the query filters, so it spans organisations, and excludes soft-deleted claims itself; the last update is `UpdatedAt`, or `CreatedAt` for a claim never changed; it is one SQL query, with the recent-breach check as a subquery); `IClaimReserveReader.ListStalePendingPostingsAsync` lists approved rows whose posting is still Pending and older than the given age.
- The claim number generator is a counter row per organisation and year, incremented with `UPDATE ... OUTPUT` inside the claim's transaction (S:CLAIMNO-Atomic), so there are no gaps. The format holds seven sequence digits, so the counter refuses past 9,999,999 with a conflict before `ClaimNumber.Create` would throw. `ClaimNumberGenerator.NextAsync` opens an explicit transaction on the context when none is open and runs one batch (update with `UPDLOCK, HOLDLOCK`, insert of the first row when none was updated, both with `OUTPUT`), so the counter row stays locked and rolls back with the claim; the Unit of Work commits that transaction right after the save, and a failed save leaves it open to roll back when the scope is disposed. The counter is a plain table (organisation and year key, last value), not an `Entity`, so it has no audit columns; it has the tenant filter, though the generator's raw SQL passes the organisation itself. The SQL runs on SQL Server only and is tested in the SQL Server test set (first number, a rollback that frees the number, parallel requests, the limit); the Unit of Work part is also tested on SQLite.
- The idempotency store is a table (`IdempotencyKeys`, in `Idempotency/`) with a unique index on key, tenant, user, method and route, the request body hash, the response status and body (a status of 0 means no response yet) and the creation time. The key is written in the command's own commit, the usual idempotent-receiver design: `BeginAsync` only reads, and for a new key adds the row to the shared context without saving, so the Unit of Work saves it together with the command, or neither is saved. A key that is saved with no response (the request is still running, or it crashed after the commit) answers `InProgress`, so a retry never runs the action again; it stays so until the key expires. A finished key answers `Completed` with the stored response, another body `BodyMismatch`, and a row older than 24 hours is restarted as new (`Started`). The unique index decides two concurrent requests with the same key: the loser's commit fails as a whole and the Unit of Work reports the conflict (tested in the SQL Server test set). `CompleteAsync` stores the response in its own save, and also saves a staged key when the command committed nothing (a refused command), so it relies on the handler never leaving unsaved changes behind on a refusal. The creation time is a concurrency token for two requests restarting an expired key. The key must fit 200 characters, so the API rejects a longer one. Deleting expired rows is a cleanup job in Infrastructure. `PurgeExpiredAsync` deletes the keys older than that 24-hour window of every organisation, 500 rows per statement until none are left (it ignores the query filters, because the cleanup job has no user).

## Migrations and seed data

- Migrations are generated by tooling and never hand-edited; `dotnet ef migrations add` and `database update` need the user's go-ahead (`.claude/CLAUDE.md` 'Permissions model').
- Seed data (policies, cause-of-loss codes) uses `HasData` or migration scripts, never application startup. A GUID in seed data is allowed; a hard-coded GUID in logic is not (S:DATA-NoHardGuids).
- The migrations sit in `Schema/Migrations/` (`Initial`, then `ClaimListViewAndAuditGrants`) (marked generated code in `.editorconfig`, skipped by the ASCII check). Tooling runs from `backend/` with the local tool: `dotnet dotnet-ef migrations add <Name> --project src/ClaimsModule.Persistence --output-dir Schema/Migrations`. `Schema/` holds the migrations, the seed and the design-time factory. `DesignTimeDbContextFactory` builds the context for tooling without the API host; it reads `CLAIMS_DB_CONNECTION` and falls back to LocalDB.
- `ClaimListViewAndAuditGrants` adds SQL by hand to the generated migration, because EF creates neither views nor grants: it creates `dbo.ClaimListView` (the same select as `Schema/ClaimListView.cs`, which the SQLite test database uses; the migration keeps its own literal copy, so a later change to the select needs an `ALTER VIEW` migration) and denies update and delete on `ClaimAuditLog` to the role `claims_app` (S:AUD-NoUpdateDelete). The deployment adds the app's database user to that role; a login that owns the database, such as LocalDB with a trusted connection, is not bound by the deny, so locally only the append-only interceptor enforces it.
- The seed lives in `Schema/Seed/`: `PolicySeed` (five policies and their nine coverage types) and `CauseOfLossSeed` (ten active codes) pass anonymous objects to `HasData`, matched by property name to mapped and shadow properties, so the Domain stays closed. Seed ids are derived from fixed names (`SeedIds.For`), with one fixed organisation and system user. Seed rows bypass the interceptors, so they carry the audit and soft-delete columns, and they also load into the SQLite test databases (tests read them with the filters ignored).
- A naming test over the EF model checks that table names equal the specification's list and columns are PascalCase (S:DATA-Naming).

## Claim aggregate and list reads

- The claim maps with its loss event (one to one), parties, risk objects, issues and state changes as marked relationships, so a child change moves the claim `RowVer`; the components and documents point at `Claims` with marked foreign keys. `ClaimRepository.GetAsync` loads the whole aggregate with a split query.
- The claim number is stored as text through `ClaimNumberConverter` with a unique index per organisation (S:BR-C-04). State is a converted closed set, severity the enum name.
- The claim list reads a keyless type (`ClaimListRow`) mapped to the `ClaimListView` database view, which joins claims, loss events and policies with the soft-delete tests written out; the tenant filter is applied on the type. Filters, count and page run in SQL; the reserve totals of the page come from the Domain balance of the page's components, so the rule stays in the Domain. The loss date range is compared in UTC days (`DateTimeOffset` comparisons on the view do not translate on SQLite, and the SQL Server test set does not cover the date filter yet). The joins in the list SQL also match the organisation of the claim, so another tenant's policy name cannot appear.
- The policy reader reads the date shadow columns by `EF.Property`, builds `PolicyPeriod` and fills the status from the clock; coverage types load in one query per page.
