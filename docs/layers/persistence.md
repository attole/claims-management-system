# Persistence layer

Persistence's schema conventions, Domain mapping, save interceptors, Unit of Work, readers, repositories and migrations; it implements the ports the Application defines (`docs/layers/application.md` 'Provides and expects'). `.claude/CLAUDE.md` points here; read this file before changing or reviewing Persistence code. Schema departures from the specification: `docs/ARCHITECTURE.md` 'Schema departures from the spec'.

## Layout

- One `IEntityTypeConfiguration<T>` per entity, Fluent API only. Converters, repositories, readers, interceptors, read-model rows and migrations have their own folders; `PersistenceServiceExtensions` registers them. A standalone feature with its own table and no Domain aggregate has one folder with its row, configuration, service and reader (`Audit/`, `ClaimNumbers/`, `Idempotency/`); the interceptors stay in `Interceptors/` because they serve every table.
- The interfaces Persistence implements are defined in the Application. The Domain is never referenced for a Persistence concern.
- Test folders mirror source folders; round trips use SQLite in memory, where the test context maps every `DateTimeOffset` to a binary value so SQLite can compare and order them (except on the claim list view, which keeps the stored text).
- `ClaimsModule.Persistence.SqlServerTests` migrates a fresh database on LocalDB (or the server in `CLAIMS_TEST_SQLSERVER`) per run, drops it afterwards, and skips every test when no server answers. It checks the migrations against the model, the seed, the claim list view and its loss-date filter, the audit grant (as a user in the `claims_app` role), the claim number SQL, the duplicate-key translation and the `RowVer` conflict.

## Schema conventions

- Primary keys are sequential GUIDs from the Domain (`Ids.Next()`), with a `NEWSEQUENTIALID()` default so the schema matches the specification.
- A column the Application validates takes its length from the Application's field-length constants (`DocumentFieldLengths`, `ReserveFieldLengths`, `ClaimFieldLengths`), never a second literal; a missing constant is added to the Application with its validator rule first, so a valid request cannot overflow its column. A column with no validator keeps its own length.
- Money is `DECIMAL(19,4)` (`HasPrecision(19, 4)`), timestamps `DATETIMEOFFSET(7)` in UTC, short codes `NVARCHAR(50)`.
- Table names are the specification's section 9: `Claims`, `LossEvents`, `ClaimParties`, `ClaimRiskObjects`, `ClaimReserveComponents`, `ReserveHistory`, `ClaimDocuments`, `ClaimAuditLog`, `CauseOfLossCodes`, `Policies`. Entities keep their Domain names and map with `ToTable` (`ReserveComponent` to `ClaimReserveComponents` with its state column named `Status`). Columns are PascalCase. Tables the specification does not list: `ClaimIssues`, `ClaimStateChanges`, `PolicyCoverageTypes`, `ClaimNumberCounters`, `IdempotencyKeys`.
- Every business table has audit columns, a tenant column and global query filters for tenant and soft delete. A table soft-deletes (`IsDeleted`, `DeletedAt`) exactly when its entity implements `ISoftDeletable`; the others (state changes, reserve history) keep their rows, and a `Remove` on them throws. The audit log and the state changes are append-only (`IAppendOnly`: any change or remove throws); the reserve history is not, because approval and posting update its row. A removed party is deactivated (`IsActive`).
- Aggregate roots (claim, reserve component, document) carry a `RowVer` concurrency token.
- A Draft claim may be incomplete: the loss date column is nullable and the cause code has no foreign key.
- **Audit log:** no update or delete permission for the application, and an index by claim and event type for the SLA dedupe lookup. `AuditLogService` takes the organisation from the claim (the tracked claim, else a lookup that ignores the filters), not from the current user, because a job has no organisation; it only adds a row, which the Unit of Work saves with the command. The interceptor stamps `CreatedAt` and `UserCreated` (null for the system actor) and throws on a changed or removed row. Its relationship to the claim does not mark the root modified, so an audit row never moves the claim's `UpdatedAt`, which the SLA job reads. The reader pages newest first, by `CreatedAt` then `Id`, both descending.
- One `ClaimsDbContext` serves every repository, reader and service, so one save covers a command. A model-wide convention adds the audit shadow columns, the soft-delete columns (`ISoftDeletable` only) and the key default to every `Entity`.
- **Query filters:** a configuration derives from `TenantConfiguration<T>` (any `ITenantOwned` type, including the counter and the list read model) or from `SoftDeleteConfiguration<T>` for a soft-deletable entity, and its `Configure` starts with `base.Configure(builder)`, which applies the filter; the soft-delete filter reads the flag through the interface property. A configuration takes the `ClaimsDbContext` in its constructor, so `ClaimsDbContext.ApplyConfigurations` registers each by hand; a test fails when a configuration is not applied or an entity has no filter. The filter reads `CurrentOrganisationId` through the context, which EF re-binds per instance, never a Guid taken at model build, which the cached model would freeze.
- The tenant filter reads the organisation of `ICurrentUser`. The posting job runs under its row's organisation, so the filter applies to its writes (`docs/layers/infrastructure.md` 'Jobs'). Any other job has no user: the filter sees an empty organisation without throwing, and job readers bypass it on purpose (`IgnoreQueryFilters` with the soft-delete test written out).
- A policy's coverage types are a child table (`PolicyCoverageTypes`, one row per type), not a JSON column.
- `CauseOfLossCodes` carries a `SortOrder` shadow column for display order; the Domain has no order.

## Mapping the Domain

- **Details values** (`LossDetails`, `PartyDetails`, `RiskObjectDetails`, `ReserveHistoryDetails`, `ClaimDocumentDetails`) are complex properties in the entity's table, replaced whole; EF marks only the changed members modified. Every member gets `HasColumnName`, because the default carries a `Details_` prefix. EF binds a record's constructor to mapped members, so a value with a member that has no column of its own (`PolicyPeriod.PolicyId`) is not a complex property.
- **Policy** maps its dates as scalar shadow columns (`EffectiveDate`, `ExpirationDate`, nullable `CancelledDate`) and ignores `Period` and `CoverageTypes`; no repository loads a Policy. The policy reader reads the columns by `EF.Property`, builds `PolicyPeriod` (a NULL cancellation date becomes `DateOnly.MinValue`), fills the status from `PolicyPeriod.StatusOn(today)` with the date of `IClock` and loads coverage types in one query per page; the status column is not stored.
- **Entities** have a private parameterless constructor with empty placeholders, because EF cannot bind domain constructors taking unmapped values; `EntityConstructionTests` builds each through it.
- **Absent values** are sealed records with an `Empty` instance (`LossDate`, `EstimatedLossAmount`), because EF refuses a nullable column on a non-nullable struct. The converter maps NULL to `Empty` and back (`ConvertsNulls`) and the property is optional. A value-type member cannot be optional, so a column that must be NULL for a Domain value type is a shadow column, and the reader maps NULL to the empty value. A stored zero estimate reads back as a set estimate (user decision).
- **Closed sets** use one generic converter (marker text out, record in) through the set's public `From`; plain enums use EF's text conversion. The stored text is the member name, so renaming a member breaks stored rows; an unknown text throws on read, and a test pins the stored names of each set. A converter maps one value, never an entity or DTO. It subclasses `ValueConverter` (the only way to set `ConvertsNulls`) with two `private static readonly Expression<Func<...>>` fields, `_toColumn` and `_fromColumn`, passed to the base constructor; a converter needing an argument builds the second expression in a private static method. A closed set inside details (party role and type) is a converted scalar with a maximum length.
- **Issues:** `ClaimValidationIssue` is a child collection of the claim with the finding as a complex property (code, field, message, evidence, and the severity as a scalar; the evidence column is as large as the trimmed loss description), the state as a converted scalar, and resolved time and resolver with empty defaults. Cleared issues stay as history.
- **History rows:** a child table of the component (`ReserveComponentId`) with the denormalised claim id, and the component type and `SubmittedAt` as mapped columns. Balances, review and posting details are complex properties with empty defaults, never NULL (`HasBalances` stores `IsSet`). The idempotency key is computed by the row and not stored; a second submit on the same component conflicts through the component's `RowVer`, which the root touch moves.
- EF 9 cannot index a member of a complex property, so the history table has no index on its claim id or change sequence.
- **Closed sets in queries:** compare a converted column against a local variable holding the instance (or an array of them); a `static` field is inlined as a constant and does not translate. `DateTimeOffset` comparisons do not translate on SQLite, so the stale-posting reader filters the age after projecting the few pending rows.

## Save interceptor

- Four interceptors, one job each, built by `SaveInterceptors.Create` in dependency order (EF runs them in registration order; a test pins it): `RootTouchInterceptor` (runs `DetectChanges` once, flags the roots), `AppendOnlyInterceptor` (rejects a change to an `IAppendOnly` row), `SoftDeleteInterceptor` (turns a remove into the flag and stamps `DeletedAt`; refuses a remove on a row that is not soft-deletable) and `RowStampInterceptor` (stamps created and modified, seeing the rows the earlier steps changed). A new step is added in that factory. Each derives from `SaveStepInterceptor`, which skips a save with no context and handles the sync and async hooks.
- `CreatedAt`, `UpdatedAt`, `UserCreated`, `UserModified` and `DeletedAt` are EF shadow properties, not Domain properties (user decision). An added row gets `CreatedAt` and `UserCreated`, a modified row `UpdatedAt` and `UserModified`, from the Application's clock and current user; `DeletedAt` is stamped when `IsDeleted` turns true, by the Domain or by a converted remove. `DeletedAt` and `UpdatedAt` of a soft-deleted row come from two clock reads and can differ by microseconds.
- The Domain sets only business fields: `OrganisationId` (on `Entity`, `ITenantOwned`) and `ISoftDeletable.IsDeleted` for a removed risk object or document.
- **Root touch:** a relationship whose rows must bump a root is declared with `.MarksRootModified()` (a Persistence annotation on the foreign key; a test fails when a foreign key to a root is not marked or listed as an exception). When a row is added, modified or soft-deleted, the roots its marked foreign keys point to are marked modified, so their `UpdatedAt` and `RowVer` move. The touch repeats up the chain, so a history write moves its component and then the claim, which serializes concurrent approvals across a claim's components; the SLA job depends on the claim touch. An untracked root is not touched. `RowVer` is a rowversion on SQL Server and a plain token (never regenerated) on SQLite, so a conflict test needs SQL Server.
- The interceptors reach the current user and time through Application interfaces and use member names as strings, so a test against a real context covers every interface member.

## Unit of Work and events

One `UnitOfWork` implements `IUnitOfWork` over the `DbContext`:

1. Pop the events of every tracked entity, roots and children (`ChangeTracker.Entries<Entity>()`).
2. Wrap each in an `ExtendedEvent` (new `Ids.Next()`, clock time, current user id, correlation id).
3. Run the before-commit handlers, repeating while they raise new events (at most 10 passes, then it throws, so a handler cycle fails instead of hanging).
4. Save once.
5. Run the after-commit handlers.

Tests against EF cover the order, the repeat, the context fields, and no save when a before-commit handler throws. Idempotency completion is its own save.

**Save errors:** the Unit of Work turns `DbUpdateConcurrencyException` and a unique-index `DbUpdateException` into the Application's `ConcurrencyConflictException` (409, `docs/layers/api.md` 'Errors'); nothing else is caught. The duplicate-key translation reads SQL Server errors 2601 and 2627, so it is tested in the SQL Server set; the concurrency translation is tested on SQLite through a row removed by another writer and on SQL Server through a real `RowVer` change.

## Readers and repositories

- A repository `GetAsync` returns `Result<T>` with the not-found error, scoped by claim id. `ClaimRepository.GetAsync` loads the whole aggregate with a split query.
- The reserve, document and claim detail readers load the claim's rows untracked and map through the Application's profiles, using Domain members (`ApprovedBalance`, `IsApproved`, the issue `IsCurrent`), so those rules stay in the Domain; a claim has few components and rows. Every other reader projects straight into DTOs (the cause-code reader with `ProjectTo`), and set-based readers across claims (the job readers) query in SQL.
- Computed members (`IsSet`, `IsClaimant`), the marker of a converted closed set and range comparisons on converted values do not translate to SQL; equality against an instance and `OrderBy` do. List and search queries therefore project to DTOs or use flat read models with plain nullable columns, and never filter a Domain entity with `AsEnumerable`.
- Reader facts: a pending row is `PendingApproval`; an unposted row is approved (Approved or AutoApproved) with posting Pending or Failed; an open balance is a component with an approved balance above zero; an approved reserve for payment is any Approved or AutoApproved transaction of the claim; the claim approved total is the net sum over all components.
- `ISlaClaimReader` lists Draft or Open claims not updated for 48 hours (`UpdatedAt`, or `CreatedAt` for a claim never changed) with no breach entry in the last 24 hours, in one SQL query with the breach check as a subquery; it ignores the query filters to span organisations and excludes soft-deleted claims itself. `IClaimReserveReader.ListStalePendingPostingsAsync` lists approved rows whose posting is still Pending and older than the given age. `IClaimDocumentReader.FindReferencedPathsAsync` returns which given blob paths a document row refers to, soft-deleted rows and every organisation included, for the orphan blob sweep.
- **Claim numbers:** a counter row per organisation and year, incremented with `UPDATE ... OUTPUT` inside the claim's transaction, so there are no gaps (S:CLAIMNO-Atomic). `ClaimNumberGenerator.NextAsync` opens a transaction on the context when none is open and runs one batch (update with `UPDLOCK, HOLDLOCK`, insert of the first row when none was updated, select of the value), so the row stays locked and rolls back with the claim; the Unit of Work commits that transaction right after the save, and a failed save leaves it to roll back on dispose. Seven sequence digits, so past 9,999,999 the counter refuses with a conflict before `ClaimNumber.Create` would throw. The counter is a plain table (organisation and year key, last value), not an `Entity`, with no audit columns; it has the tenant filter, though the raw SQL passes the organisation itself. The SQL is tested in the SQL Server set (first number, a rollback that frees the number, parallel requests, the limit); the Unit of Work part also on SQLite.
- **Idempotency store:** `IdempotencyKeys` has a unique index on key, tenant, user, method and route, the body hash, the response status and body (status 0 means no response yet) and the creation time, which is also a concurrency token for two requests restarting an expired key. `BeginAsync` only reads, and for a new key adds the row to the shared context unsaved, so the Unit of Work saves it with the command or not at all. A saved key with no response answers `InProgress`, so a retry never runs the action again until the key expires; a finished key answers `Completed` with the stored response, another body `BodyMismatch`, and a row older than 24 hours restarts as new (`Started`). The unique index decides two concurrent requests with one key: the loser's commit fails whole and the Unit of Work reports the conflict (tested on SQL Server). `CompleteAsync` stores the response in its own save, and also saves a staged key when the command committed nothing, which relies on a handler never leaving unsaved changes on a refusal. A key is at most 200 characters (the API rejects longer). `PurgeExpiredAsync` deletes keys older than 24 hours across organisations, 500 rows per statement until none are left, ignoring the query filters.

## Migrations and seed data

- Migrations are generated by tooling and never hand-edited; `dotnet ef migrations add` and `database update` need the user's go-ahead (`.claude/CLAUDE.md` 'Permissions model').
- The migrations are in `Schema/Migrations/` (`Initial`, `ClaimListViewAndAuditGrants`, `RestrictHistoryDeletes`), marked generated code in `.editorconfig` and skipped by the ASCII check. Tooling runs from `backend/` with the local tool: `dotnet dotnet-ef migrations add <Name> --project src/ClaimsModule.Persistence --output-dir Schema/Migrations`. `Schema/` also holds the seed and `DesignTimeDbContextFactory`, which builds the context without the API host from `CLAIMS_DB_CONNECTION`, falling back to LocalDB.
- `ClaimListViewAndAuditGrants` adds SQL to the generated migration, because EF creates neither views nor grants: it creates `dbo.ClaimListView` (the select of `Schema/ClaimListView.cs`, which the SQLite test database uses; the migration keeps its own literal copy, so a change to the select needs an `ALTER VIEW` migration) and denies update and delete on `ClaimAuditLog` to the role `claims_app` (S:AUD-NoUpdateDelete). The deployment adds the app's database user to that role; a login that owns the database (LocalDB with a trusted connection) is not bound by the deny, so locally only the append-only interceptor enforces it.
- `RestrictHistoryDeletes` makes the foreign keys of `ClaimAuditLog` and `ClaimStateChanges` to `Claims` and of `ReserveHistory` to `ClaimReserveComponents` restrict deletes.
- Seed data uses `HasData` or migration scripts, never startup. A GUID in seed data is allowed; in logic it is not (S:DATA-NoHardGuids). `Schema/Seed/` holds `PolicySeed` (five policies, nine coverage types) and `CauseOfLossSeed` (ten active codes), which pass anonymous objects to `HasData` matched to mapped and shadow properties, so the Domain stays closed. Seed ids come from fixed names (`SeedIds.For`), with one fixed organisation and system user. Seed rows bypass the interceptors, so they carry the audit and soft-delete columns; they also load into the SQLite test databases (tests read them with filters ignored).
- A naming test over the EF model checks that table names equal the specification's list and columns are PascalCase (S:DATA-Naming).

## Claim aggregate and list reads

- The claim maps its loss event (one to one), parties, risk objects, issues and state changes as marked relationships, so a child change moves the claim `RowVer`; components and documents point at `Claims` with marked foreign keys.
- The claim number is stored as text through `ClaimNumberConverter` with a unique index per organisation (S:BR-C-04). State is a converted closed set, severity the enum name.
- The claim list reads a keyless type (`ClaimListRow`) mapped to `ClaimListView`, which joins claims, loss events and policies with the soft-delete tests written out and matches the claim's organisation in every join, so another tenant's policy name cannot appear; the tenant filter is applied on the type. Filters, count and page run in SQL; the page's reserve totals come from the Domain balance of its components. The loss date range is compared in UTC days; it does not translate on SQLite, so it is tested in the SQL Server set.
