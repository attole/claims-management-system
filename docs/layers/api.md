# API layer

Rules and contracts of the API: controllers, the error body, identity, correlation, the Idempotency-Key filter, uploads and downloads. It fills the current user from the token and supplies the correlation id the Application expects (Infrastructure registers the clock and the current user holder) (`docs/layers/application.md` 'Provides and expects'). `.claude/CLAUDE.md` holds the short rules and points here; read this file before changing the API project or reviewing its code. Status: complete, with tests: every route of the specification plus four for screen elements. The decisions below were settled on 2026-10-21 and are binding; the 'Tests' section lists how each one is enforced.

## Layout

- The API project root has four things: `Controllers/` (the endpoints, with their `Requests/`: one record per query string or body, mapping itself to its Application query or command; responses are the Application's DTOs), `Errors/` (`ErrorBody`, the concurrency exception handler and `AddErrors`: the wire contract of failures, used by controllers and pipeline pieces alike), `DevAuth/` (the dev token endpoint with its issuer, its `Configuration/`, with its request and response DTOs next to the controller: a feature with an endpoint, dev-only and removable as one unit) and `Pipeline/` (everything that runs around the actions: `Correlation/`, `Cors/`, `Idempotency/`, `Identity/`, `Jwt/` and `Swagger/`). There is no catch-all `Configuration/` folder. A feature folder holds its options, its `<Feature>ServiceExtensions` class and any middleware or filter together. Anything that controllers or other layers need goes at the root; anything that only runs around the actions goes under `Pipeline/`.
- Namespaces follow the folders (`ClaimsModule.API.Pipeline.Identity`, `ClaimsModule.API.DevAuth.Configuration`), and the test project mirrors them (`ClaimsModule.API.Tests.Pipeline.Identity`). A folder is never named `Options`: the namespace would shadow `Options.Create` in the code and the tests around it.

- `Pipeline/ApiPipelineServiceExtensions` composes the features: `AddApiPipeline` calls each feature's `Add...` (the `Pipeline/` features, `Errors/` and `DevAuth/`) and `UseApiPipeline` calls each `Use...` in the one order that matters (described in the Identity and correlation section), so `Program.cs` has two calls for the API on top of the layers' own. A new feature adds its line there and keeps its own extension class.

## Controllers and routes

- A controller action maps the request to one command or query, sends it through MediatR and returns the mapped `Result`. It holds no business logic and builds no error JSON by hand.
- Routes use plural nouns in kebab-case, under `/api`. The specification's own routes keep their names even where they are not plural (`/status`, `/reference/...`); the route test allows exactly the routes listed in this section. The reserve decision routes are the specification's, which name a history row. Two assessment routes are deliberately not built (a reserve update and a combined decision route).
- Only the routes the three screens and the specification's route table need exist. Every other Application command (risk object add, update and remove, loss details, severity, limit override, assign handler, link policy, acknowledge and waive an issue, remove a document) stays without a route; the Domain and the Application carry them and a route is added when a screen needs it.
- The routes (S:API-POST-claims, S:API-GET-claims, S:API-GET-claim, S:API-PUT-claims-status, S:API-GET-claims-audit, S:API-POST-claims-parties, S:API-DELETE-claims-parties, S:API-POST-claims-documents, S:API-GET-claims-documents, S:API-POST-reserves, S:API-GET-reserves, S:API-POST-reserve-approve, S:API-POST-reserve-reject, S:API-POST-reserve-retract, S:API-GET-causes, S:API-GET-statuses, S:API-GET-policies-search):
  - the specification's table, under `/api/claims`, `/api/reference` and `/api/policies`;
  - three routes beyond the table, each for a screen element: the claim notes update (Overview tab), the retry of a failed GL posting (Reserves tab, `RetryReservePostingCommand`) and the closure pre-check below.
- Reads reuse the composed queries; every list is paged and the page size is capped by the Application.

## Closure pre-check

- `GET /api/claims/{id}/status-check?targetStatus=Closed` shows the user what blocks a transition before the click (S:UI-Detail-Header, S:BR-ST-03). It works for any target status.
- It is backed by `CheckClaimStatusQuery(ClaimId, TargetStatus)`. The handler loads the claim, runs the same transition as `ChangeClaimStatusCommand` through a runner map the two handlers share, and never commits, so no event is dispatched and nothing is saved. It uses the user and role of the request, so a reopen check answers for that role.
- It returns only the failing findings (code, severity, message, field). The frontend keeps the fixed list of the closure conditions (S:CC-01 to S:CC-04) keyed by finding code: no finding is a pass, and the warning for S:CC-04 shows the justification note field. Confirm is enabled while no Critical finding remains. The result is advisory: `PUT /api/claims/{id}/status` runs the rules again and its 422 is authoritative.
- It is a read, so the Idempotency-Key filter does not apply.

## Errors

- One error mapper turns a `Result` into the response: validation 422, not found 404, forbidden 403, conflict 409. An unknown id is always a 404, including an id that belongs to another claim or a child (a party, a reserve row) the claim does not own; only the Application creates one.
- A `ConcurrencyConflictException` from the Unit of Work (a concurrent edit or a duplicate key) is handled by `ConcurrencyConflictExceptionHandler` and returned as a 409 with the same body; the exception text is never on the wire.
- The body follows the specification's sample: `type`, `title`, `status` and `errors` grouped by field (S:API-ErrorShape). `type` is the short name of the error kind, as in the sample, not a URI: `ValidationError`, `NotFoundError`, `ForbiddenError` or `ConflictError`. `title` is readable text. An error without a field goes under the key `General`. The error code is not on the wire.
- Only a request that cannot be bound at all is rejected before a command runs, and that rejection uses the same 422 body, not an own 400 body (a missing non-nullable value included).
- A successful write returns the named envelope `CommandResponse<TData>` (`{ data, warnings }`, a record nested in `ApiControllerBase` so a derived controller names it directly in its attributes), where a warning is the Application's `Warning` record on the wire (`code`, `message`, `field`); a write without warnings returns an empty list, so the frontend reads one shape. A read returns its data directly (a query has no warnings), and a page is the Application's `PagedResult` as it is: `{ items, page, pageSize, totalCount, totalPages }`. The Application never returns HTTP types.
- Controllers derive from `ApiControllerBase` (`Controllers/`): `QueryAsync(request, ct)` sends a query and returns its data, and `CommandAsync(request, ct)` sends a command and returns the envelope. A failed `Result` becomes the error body in both. `ErrorBody` (`Errors/`) owns the body: `From(errors)`, `Create(kind, message)`, `Unauthorized()`, `FromModelState(...)`, `ToResult()` and `WriteAsync(context, cancellationToken)`. `ErrorsServiceExtensions.AddErrors` replaces the framework's model-state response with the 422 body through `PostConfigure` (an earlier `Configure` would be overwritten by `AddControllers`), registers `ConcurrencyConflictExceptionHandler`, an `IExceptionHandler` that turns a `ConcurrencyConflictException` into the 409 body (the existing `UseExceptionHandler()` runs it), and adds the error responses (401, 403, 404, 409, 422 with `ErrorBody`) to the OpenAPI document of every action.
- The success status of an action is declared, not passed: a write action carries `[ProducesResponseType<CommandResponse<TDto>>(StatusCodes.Status201Created)]` (or 200, and so on) and a read action `[ProducesResponseType<TDto>(...)]`. `CommandAsync` reads the one declared 2xx status from the action's metadata, defaults to 200 when none is declared, and throws when an action declares two, so a misdeclaration fails loudly. The same attribute is what the OpenAPI document shows, so the status and the documentation have one source. Every action of a controller derived from `ApiControllerBase` declares its success response explicitly; a test enforces it (see 'Tests').
- 401 and 403 use the same body: the JWT handler's challenge writes `UnauthorizedError` (with `WWW-Authenticate: Bearer`) and its forbidden event writes `ForbiddenError`; the current-user middleware's 401 and the dev token's 404 use the same writer. A request with a missing or wrong `Content-Type` is the framework's own 415, which is outside this contract.

## Identity and correlation

- The actor and the role come from the authenticated user, never from the request. The role from the token becomes a `UserRole` with `UserRole.From`, and only an exact role name is accepted (`RoleNames.IsKnown`): a number, a comma list, different casing or padding is refused, in the token and in the dev user settings alike.
- Authentication is a bearer token (S:API-Auth). The claims are `sub` (the user id), `org` (the organisation id), `role` (`Handler`, `Supervisor` or `Manager`) and `name` (for the header display). `sub` is the standard JWT subject claim; the inbound claim mapping stays off so the middleware reads the names as written.
- Persistence builds `ClaimsDbContext` and its save interceptors from the scoped `ICurrentUser` and `IClock`, so the API must register `IClock` (Infrastructure registers it) and `ICorrelationContext`, and a middleware right after authentication sets the scoped `ScopedCurrentUser` that Infrastructure registers as `ICurrentUser` (id, organisation and role from the token) before any request reaches a handler. The organisation of the user is the tenant filter value; the dev users carry the seeded organisation id, or the seeded policies and cause-of-loss codes are invisible to them (`docs/layers/persistence.md` 'Migrations and seed data').
- Dev token (the specification asks for a mock authentication service): a `DevTokenIssuer` and a `DevAuthController` with `POST /api/dev/token` live in the API's `DevAuth/` feature folder (the controller, the issuer and the extensions at its root, `Configuration/` for the options and their validator, `DevTokenRequest` and `DevTokenDto` beside the controller), behind `DevAuth:Enabled`. The users and the seeded organisation id are settings. There is no Application port and no Infrastructure token service. The request is `{ userId }` and the response carries the token, its expiry and the user; an unknown user, or `DevAuth:Enabled` false, answers 404. The options are validated at startup while the switch is on, and the token lifetime is capped at 1440 minutes. It is a simulation and is documented as one in the README (Swagger documents it when pack 7 adds the note).
- Anonymous routes are only the dev token endpoint, Swagger and the signed local download route. Every other action requires an authenticated user, and a test enforces it.
- Role checks stay in the Domain rules (`HasApprovalAuthority`, `HasRejectionAuthority`, `IsNotSelfApproval`, the reopen transition) (S:ROLE-Enforcement). A role failure is therefore the 422 of its finding, with the specification's message. No action uses `[Authorize(Roles = ...)]`; the API requires an authenticated user and nothing more. One source of truth keeps the message and the status the same however the rule is reached.
- Correlation (S:AUD-Correlation): a scoped `CorrelationContext` holds a new GUID for every request (a job scope gets its own), so every audit entry of the request reads it, and a middleware at the start of the pipeline returns it as the `X-Correlation-Id` response header when the response starts (so an error response carries it too). An incoming `X-Correlation-Id` is ignored, because it is untrusted input and the audit column is a GUID. Accepting a valid inbound GUID is the extension if a gateway is ever added.
- The Hangfire dashboard cannot be protected by the bearer token, because a browser page cannot send the header. It stays behind its feature switch (default off, on only in development) and is documented as open to every request when on. It must not be enabled in a deployed environment. Because the fallback policy covers every request after the authorization middleware, `ApiPipelineServiceExtensions.UseApiPipeline` adds the dashboard (`UseInfrastructure`) and Swagger before `UseAuthentication`, and the OpenAPI document is mapped with `AllowAnonymous()`; the pipeline order, written once in `ApiPipelineServiceExtensions.UseApiPipeline`, is correlation, exception handler, HTTPS redirection, CORS, dashboard, Swagger, authentication, current user, authorization, controllers.

## Idempotency-Key

A write operation with an `Idempotency-Key` header is idempotent (S:API-IdempotencyKey). The specification applies it to all write operations when the header is provided, so there is no exemption, uploads included. It is a global resource filter (not a MediatR behavior, because only the API knows the header, the route and the final status and body). A resource filter runs before model binding, which is the only point where the raw body can still be read. The request size and form limit attributes of an action are authorization-stage filters, so they have already raised their limits before this filter reads the form.

1. A key longer than 200 characters (the column length) is rejected with the 422 body before anything else.
2. Before the action the filter hashes the request and calls `IIdempotencyStore.BeginAsync` with the key, method, route (the request path) and hash. The hash covers the body only; the user, the organisation, the method and the route are part of the store's own key. A JSON body is hashed as is. A form or multipart body is hashed by its fields and files (name, file name and bytes), never by the raw body, because the multipart boundary is random for every request and would make every retry a mismatch; a file of up to 50 MB is one extra sequential read through request buffering.
3. `Started`: run the action. `Completed`: return the stored response without running it. `InProgress`: return 409. `BodyMismatch` (the same key with another body): return 422.
4. After the action the filter calls `CompleteAsync` with the status code and body.

The store saves the key with the command's own commit, so a key with no stored response means the request is still running or crashed after its commit: it answers 409 and the action is never run again until the key expires. Completion (the response) is its own save after the action.

The header is optional and the filter applies to every write action; a request without it runs normally and is not stored. A replay returns the first response even if the claim has changed since; fresh state comes from a read. A stored key expires after about 24 hours and then counts as new (the cleanup job in `docs/layers/infrastructure.md` removes the rows).

## Wire format

- Lists are paged with `page` and `pageSize` query parameters, and the response is the Application's `PagedResult` (`items`, `page`, `pageSize`, `totalCount`, `totalPages`); the Application caps the page size.
- JSON is camelCase. Closed sets (statuses, roles, components) are their names as strings, dates and times are ISO 8601, money is a number.
- Filters of the claims list bind from the query string with the names of the specification (`status`, `dateFrom`, `dateTo`, `assignedHandlerId`, `causeOfLossCode`, `policyId`, `search`). `status` repeats for a multi-select (`status=Open&status=Draft`) and maps to the Application's `Statuses`.
- The default page is 1 with 25 rows (`PagingDefaults`); a page size above 100 answers 422.
- Reserve routes under `/api/claims/{claimId}/reserves`: `GET /` (summary and history), `POST /` (201, the body is the Application's `ReserveRequest`), `POST /{reserveHistoryId}/approve`, `POST /{reserveHistoryId}/reject` (body `{ rejectionReason }`), `POST /{reserveHistoryId}/retract` and `POST /{reserveHistoryId}/retry-posting`. The role and no-self-approval checks are Domain rules, tested in the Domain and Application tests; the API tests cover the wiring (401, 404, 422).
- Document routes under `/api/claims/{claimId}/documents`: `GET /` (links) and `POST /` (201, multipart with `file`, `documentType` and `notes`); the upload action raises its request size and form limits to 51 MB so the Domain's 50 MB rule answers 422. The anonymous `GET /api/documents/download?token=` serves the local provider's files.
- Claim routes under `/api/claims`: `POST /` (201, the draft with its children in one call), `GET /{claimId}`, `PUT /{claimId}/status`, `GET /{claimId}/status-check?targetStatus=`, `PUT /{claimId}/notes`, `GET /{claimId}/audit`, `POST /{claimId}/parties` (201) and `DELETE /{claimId}/parties/{partyId}`. Bodies bind to a record in `Controllers/Requests/` that maps itself to its command (`ToCommand`), except the party body, which is the Application's `PartyRequest`. An Application request type that carries its own validator is used as a body as it is.
- Enums travel as their names in both directions (a `JsonStringEnumConverter` on the controllers); an unknown name is a 422.
- Reads: `GET /api/claims`, `GET /api/policies/search?q=`, `GET /api/reference/cause-of-loss-codes` (optional `perilCategory`), `GET /api/reference/claim-statuses` (each status with its allowed next statuses). Each query string binds to a request record that maps itself to its query.

## Documents

- The upload is multipart (S:API-POST-claims-documents). The size and the type rules are Domain rules (S:DOC-MaxSize, S:DOC-MimeAllowlist), so the user gets their 422 message. The server must not reject first: Kestrel's default request body limit is about 28.6 MB, so the upload action raises its request size limit to just above 50 MB (the Domain limit plus the multipart overhead), and a larger body is refused by the server (the form read fails with a request-body-too-large message and the API answers 422 in the usual error body).
- The document list returns a download URL for each file (S:API-GET-claims-documents). For Azure it points at the blob; for the local provider the API serves the signed route and streams what the Application port `ILocalDocumentDownloads.Open(token)` returns. The Infrastructure implementation (`LocalDocumentDownloads`) validates `LocalDownloadToken`, checks that the provider is the local file system, finds the file and names it; under Azure it returns nothing, so the route answers 404. The file name is the original name behind the upload id in the blob path, and the content type comes from its extension (octet-stream when unknown); the route reads no database row, so the tenant filter is not involved. An invalid, tampered or expired token answers 404, and a missing `token` parameter 422. The token is the only check on that route, which is why it is anonymous. Static files are not used.

## Swagger

- Swagger shows a bearer authorize button and a note that the dev token is a simulation (`Swagger:Enabled`, default off, on in development).

## Tests

The rules above are enforced by tests; a rule without a test here is a rule to add one for.

- A route test checks that every route is kebab-case plural (S:DATA-Naming), with the listed exceptions as an explicit allow-list.
- Three route-driven tests walk every route from the action descriptors instead of one test per controller: every route without a token answers 401, and every claim read route answers 404 for an unknown claim and for a claim of another organisation. A new route is covered without a new test. Write routes keep their own tenant and validation tests, because they need a valid body.
- One journey test drives the main flow through the real pipeline: an open claim, a reserve submitted and approved by two users, the move to pending payment, then the detail and the audit.
- A reflection test checks that no action uses `[Authorize(Roles = ...)]`, that every action is authenticated except the three anonymous routes, that every write action is covered by the Idempotency-Key filter, and that every action of a controller derived from `ApiControllerBase` declares exactly one 2xx `[ProducesResponseType]` (a write action with `CommandResponse<>` as its type).
- The error mapper has a test per error kind (status and `type`), for the `General` key and for the concurrency conflict exception handler.
- The Idempotency-Key filter has a test per outcome (`Started`, `Completed`, `InProgress`, `BodyMismatch`), one for a key over 200 characters and one for a multipart upload.
- The correlation middleware has a test that it ignores an incoming header, returns a new GUID in `X-Correlation-Id` and exposes the same value through `ICorrelationContext`.
- The pre-check has a handler test per closure condition and a test that `CommitAsync` is never called.
- The upload action has a test that a body just under 50 MB reaches the Domain and one that a larger body is refused by the server.
- The API tests run on `WebApplicationFactory` against LocalDB (or `CLAIMS_TEST_SQLSERVER`) and skip when no server answers, like the SQL Server tests of Persistence; when `CLAIMS_TEST_SQLSERVER` is set and the server does not answer they fail instead of skipping. One shared fixture migrates the database once, and every test creates its own organisation (`CreateOrganisationAsync` gives it one active cause code), so the tenant filter isolates the tests from each other. The reserve tests need a policy, so they use the seeded organisation and the helper `SeedOpenClaimAsync`, which builds an open claim with a linked policy and a unique claim number.
- The test host removes every hosted service, which stops the Hangfire server; the startup validation of options still runs (a test proves that a bad dev user stops the host). It replaces `IPostingScheduler` with a recording fake and `IRecurringJobManager` with a mock, so a test proves which jobs are enqueued and never runs one. The real Hangfire path is checked by the Infrastructure tests (`docs/layers/infrastructure.md` 'Tests'). Four API tests run on a real Kestrel host (`KestrelApiFactory`): the upload just under the limit reaches the action with a key, and one over the limit is refused with the form-read error.
