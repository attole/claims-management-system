# Domain layer

The Domain's code shapes, model rules, folders and engine, and its contract with the Application. `.claude/CLAUDE.md` points here; read this file before changing or reviewing Domain code.

## Code shapes

Each kind of class has one shape.

- **Rule:** an `internal` class with constants `Code` (public), `Message` and `Field` (private) and one `Check` method that names the statement in a `bool` true when the rule passes (`bool hasClaimant = ...;`, `bool isNotLastClaimant = !...;`) and returns `statement ? Pass : Found(finding)`. A rule built from the input takes plain values through a primary-constructor parameter (`HasNoPendingReserveHistory(bool hasPendingReserveHistory)`), never a whole input or facts record. The statement reads a fact on its owner ('Domain modeling'), so the rule only maps the fact to its code and message. A rule that does not read its subject checks `object` (`IRule<object>`) and serves any step, `NoSubject` included; a rule about a shared concept lives with that concept, never in `Core` (`Roles/Rules/HasMinimumRole`). A combined rule (`HasValidLossDetails`, `IsLossCompleteAfterDraft`) runs other rules over one part of an aggregate and returns their findings: it has a `Code` but no `Message`, `Field` or finding of its own.
- **Operation:** an `internal` class in `Flows/` naming itself as the first type argument of its base (`Operation<AddPartyOperation, Claim, AddPartyInput, ClaimParty>`), its input a type of its own in `Inputs/` (public for an aggregate method, internal for a child's method). The constructor only calls `Require`; the class has no fields ('Domain engine'). `Apply` changes the subject through its `internal` members and returns `Done(...)` with the added child, the root itself when it changed its own fields, or, for a change to an existing child, the outcome of that child's method; it holds no condition, does not touch the root and raises no event.
- **Evaluation over a whole entity:** an `internal` operation in `Flows/` (`EvaluateIssuesOperation`) whose only required rule is that the claim is editable, so a frozen claim keeps the issues its closure was judged on; the issue rules are not required, because a required Critical rule would stop the step. `Apply` checks them in one private static method (`CheckResult.Combine`), builds a few named queries over the findings and loops over them.
- **Transition:** an `internal` class in `Flows/` deriving from the aggregate's transition base with itself as the first type argument (`ClaimBaseTransition<OpenClaimTransition, ClaimTransitionInput>`); its input is the aggregate's transition input or a record in `Inputs/` deriving from it (`FreezeClaimInput`). The constructor names the target and declares each `AllowedFrom(...)` with its rules. The engine seals `Check` and `Apply` and returns the `Move` (from, to); the aggregate's base seals `ApplyMove`, which sets the state (and on the claim appends the history row). Nothing is overridden.
- **Entity (child):** constructors (private for EF, then `internal` with `id`, parent id, organisation id and its data, a details record where the data is editable), properties, then `internal` methods, one per change, each running the child's own step on itself (`party.Remove()`, `riskObject.Remove(input)`) and raising the child's events in its follow-ups. Fields a step sets have `internal` setters. Audit columns are not Domain state: Persistence stamps them.
- **Aggregate root:** fields with `internal` setters and child lists behind `internal` accessors; the follow-up helpers are `private` methods. The issue evaluation returns the issues it raised and cleared (`IssueChanges`): the root raises the raised events, and each cleared issue raises its own event through `issue.Clear()`, like an acknowledged or waived one.
- **Aggregate method:** a `public` method that takes the step's input record only (outside facts the follow-ups need ride on it, like `PolicyPeriod` and `CauseCodes` on every claim input) and returns one chain: `Step.Run(this, input)`, one `.OnSuccess(...)` per follow-up in order (raise the event, record the move, run an inner step), and on the claim `.OnSuccess(() => Settle(input))` last (the issue re-evaluation). A claim move also calls `Settle(input);` before the chain, so the transition's rules read issues evaluated with the move's facts. A follow-up is an inline lambda constructing its event in one line (`party => Raise(new PartyAddedEvent(Id, party.Id, party.Details.Role.Name))`); it is a private method only when reused, running an inner step, or building an event that does not fit one line (`Settle`, `RecordMove`, `OpenAfterReopen`, `RecordRaisedIssues`; `RecordSubmission` and `AutoApprove` on the reserve component, `CancelPosting`, `RecordApproval` and `RecordPosting` on its history row). The chain holds no rule and never changes the outcome. A creation method is static, named by the domain verb (`Claim.Create`, `ReserveComponent.Open`), and its hooks take the created aggregate (`claim => claim.Settle(input)`).
- **Details record:** identifying values positional, optional ones `{ get; init; }` with an explicit empty default.
- **Closed set:** one file named after the base type holding the marker enum, the abstract record and the sealed variants with `() : Base(Kind.Value)`; a variant with behavior overrides the base member in a body.
- **Event:** a positional record `<Thing><PastVerb>Event(<ids and facts>) : DomainEvent`, one parameter per line, carrying business facts only; its id, time and actor come from the extended event the Application wraps it in at dispatch.
- **Options and extension classes** are in `.claude/CLAUDE.md` 'Core rules'.

## Domain and Application

- The Domain holds state (aggregates, children, value records, closed sets), rules (a statement about one subject and the request, a class with a `Code`) and single steps (an operation, creation or transition that changes one aggregate in `Apply`).
- An aggregate's public face is its methods: each is a chain on one step's outcome, with the follow-ups inside the same aggregate and `Settle` last. Steps and rules are `internal`; inputs, events, outcomes and findings are the public contract.
- The Domain never loads or saves, reads no clock (except `Ids`), knows no identity, reads no other aggregate (a static fact on a type, such as `Claim.IsWithinReserveLimit`, is not a read), returns no HTTP type and never chains across aggregates.
- The Application loads, builds the input with the outside facts, calls one aggregate method, reads its outcome, commits through the Unit of Work (which dispatches the events) and maps findings. It holds no statement about state.
- A true-or-false statement about state and request is a rule; a change to one aggregate is a step; a second aggregate, a load, a save, a clock, an identity or a job is Application; a value from outside the aggregate is computed by the Application into an input field; an effect that crosses a boundary (audit, a job) is a domain event with an Application handler.

## Domain modeling

- **No invented rules:** a rule no source states (a bound on an amount, a length) is not added; ask for the source. A rule's `Code` constant is the source-qualified ID when a document states the rule (`S:BR-C-05`), else an upper-snake code for a rule guarding the system's own contract (`CLAIM_NUMBER_REQUIRED`); the constants are the only list, and rules enforcing one source rule share its code. The failing line reads `CheckResult.Found(new Finding(Code, Message, Field))`.
- **Facts on their lowest owner:** a fact about one entity, value or closed set lives on it (`change.IsSubmittedBy`, `details.CanHoldBalanceAfter`, `state.IsEditable`, `lossDate.IsAfter`, `causeCodes.IsActive`, `role.HasRightsOf`); a fact about a list of children lives on the root that holds it (`claim.HasActiveClaimant`, `claim.IsOnlyActiveClaimant`, `claim.HasOtherPrimaryRiskObject`, `claim.HasUnresolvedWarning`). Rules with different codes share one fact, so no logic is written twice.
- **Time and actor:** the only clock read is `Ids.Next()`, which reads UTC time to order new ids (a technical value). Every claim input carries `Now` through `ClaimBaseOperationInput` (every claim method re-evaluates the issues, and the loss date is checked against it); an input whose step records a person's decision also carries `ActorId`, stamped once by the Application. The reserve history's submit and decision inputs carry their own time. `InputTime.Required` and `InputActor.Required` refuse a missing time or actor, and `InputTime.NotBefore` a business time earlier than the one it follows (a review before the submission, a resolve or delete before the claim's reported date); all three throw, because the Application stamps them. An automatic issue clear records no time or actor. Time and actor feed business rules and records only, never audit columns or event metadata. A calendar day derived from a timestamp is its UTC day.
- **Entities:** a child keeps its editable data in one immutable details record, replaced whole with `with`. Capability interfaces are get-only; fields a step sets have `internal` setters, the others private; mutators are `internal`.
- **EF friendliness:** every entity has a private parameterless constructor with empty placeholders, built by a test. A value that may be absent is a sealed record with a static `Empty` and an `IsSet` flag. List and search queries use projections or read models, never filtered Domain entities.
- **Creation:** `CreateClaimOperation` creates a minimal valid Draft; parties, risk objects and loss details are added by the same operations as later edits.
- **Document content:** `DocumentContentTypes` is the one table of allowed content types and their content signatures. `IsContentTypeAllowed` (S:DOC-MimeAllowlist) checks the declared type against it, and `IsContentMatchingType` (`DOC_CONTENT_MISMATCH`) checks the file's first bytes (`UploadClaimDocumentInput.Header`, at most `HeaderLength`, 512) against that type's signature. `IsFileSizeAllowed` is S:DOC-MaxSize.

## Domain folders

Top level: `Core/` (the engine), `Common/` (entity and event base types, capability interfaces, markers, `Ids`, `InputTime`), `Roles/` (user roles and their rule, shared by the aggregates), and one folder per aggregate: `Claims/`, `ReserveComponents/`, `ClaimDocuments/`, plus the reference data the claim points to by id, with no operations: `Policies/` (the policy and its period) and `CauseOfLoss/` (the cause-of-loss code and the `CauseCodes` value the claim inputs carry). An aggregate folder holds the root (`Claim.cs` and its values: state, number, severity) and its role folders; `ReserveComponents/History/` holds the history row entity.

- `Claims/` holds one folder per child entity (`Parties/`, `RiskObjects/`, `Loss/`, `Issues/`, `StateChanges/`), each shaped the same way.
- A folder holds the entity or root, its closed sets and values, and the subfolders it needs: `Inputs/` (public method inputs, base inputs, and the internal inputs a parent builds for a child's method), `Events/`, `Flows/` (operations and transitions) and `Rules/` (every rule about the entity; whether a finding refuses a step or becomes an issue is decided by the step or evaluation that requires it). A base lives with what it is a base of: a base input in `Inputs/`, the base transition in `Flows/`. The root, `Inputs/` and `Events/` are public; the rest is internal.
- Steps and rules spanning entities live in the aggregate's own `Flows/` and `Rules/`; the aggregate's step for a change to a child (`<Verb><Thing>OnClaimOperation`) and its rules about a child collection (`IsNotLastClaimant`) live in the child's folder.
- **Inputs per method:** every method takes one input record with exactly the data it needs and does not already have. An aggregate method's input is request data plus outside facts (actor, time, policy period, cause codes, plain reserve facts), never the aggregate's own data. Steps needing the same data share a record (`ClaimTransitionInput` for open and investigate, `RowPostingInput` for the posting moves), and a step needing more derives from it, so a step that reads no role gets none: `RowDecisionInput` (retract) is extended by `RejectRowInput` (the role) and the abstract `RowApprovalInput` (the balance facts), which `AutoApproveRowInput` (no reviewer) and `ApproveRowInput` (role and override) extend; `FreezeClaimInput` (close and withdraw) and `SendToPaymentClaimInput` add reserve facts, and `ReopenClaimInput` adds the role. The reserve component's public inputs (`ApproveHistoryInput`, `RejectHistoryInput`, `RetractHistoryInput`, `HistoryPostingInput`) carry the row id, and its step builds the row's internal input with the balance from the component's `ApprovedBalance`. A child's method takes an internal record from the child's `Inputs/` (`RiskObjectDetailsInput`, `IssueResolutionInput`), built by the aggregate's step from its input and, when needed, from the aggregate's own fields (`this.State`), never the whole aggregate; a method that needs nothing takes `NoInput`.

## Domain engine

`Core` is generic and layered (`Core/Rules`, then `Core/Flows`): a layer uses only the layers before it, `Core` and `Common` reference neither `Roles` nor an aggregate, `Common` does not reference `Core`, `Roles` references no aggregate, and `Core` holds no business rule. Reasons: `docs/ARCHITECTURE.md` 'Engine'.

- A step declares its rules once in the constructor with `Require`: a ready instance, or a rule built from the input (`input => new IsNotLastClaimant(input.PartyId)`).
- A step is one shared instance, built on the first call and reused; `Run(subject, input)` is static (`AddPartyOperation.Run(this, input)`). A step keeps no state beyond its rules (a transition also keeps its target and its rules per source).
- The machinery (`Operation`, `CreationOperation`, `Transition`, `RuleSet`, `IRule`, `CheckResult`) is `internal`; the result side (`Outcome`, `Finding`, `FindingSeverity`, `NoSubject`, `NoInput`, `Move`) is public. On `Outcome` only `IsSuccess`, `Value`, `CriticalFindings` and `WarningFindings` are public; `OnSuccess` and the factories are `internal`.
- `Outcome.OnSuccess(hook)` runs the hook when the step succeeded and returns the same outcome; it never adds a finding or changes the value. A condition that could refuse is a rule on the step.
- Vocabulary: a rule is checked (`rule.Check`, `rules.Check`) and its `CheckResult` passes (`Pass`) or holds what it found (`Found`); a step succeeds or fails (`IsSuccess`); a move from a state the transition does not allow is refused with `TransitionCodes.NotPermitted` (public, so the Application can recognise it); evaluate means check the issue rules and record the issues (`EvaluateIssues`); an issue is a stored finding on a claim with its own lifecycle (raise, clear, acknowledge, waive). "Check" is only a verb.
- One finding type, `Finding` (code, message, field, severity, evidence), Critical by default, `AsWarning()` for a Warning. A rule that checks a value puts it in the evidence; an issue matches its finding by code and evidence, so a waiver or acknowledgement lapses when the checked values change. Every operation and transition stops on a Critical finding; a warning that must block is its own rule with a Critical finding (`HasNoUnacknowledgedPolicyWarning`). The issue evaluation stores each finding of the issue rules unchanged.
- A part of an aggregate with several rules (the claim's loss) has one combined rule (`HasValidLossDetails`) with the outside facts in its constructor; the issue evaluation checks it over the stored loss, the edit guard after Draft over the proposed values.
- "Not allowed in that state" is a rule that reads the state, never a conditional in an operation.
- A change to an existing child is split by subject. The aggregate's step (`<Verb><Thing>OnClaimOperation`, in the child's `Flows/`) holds only aggregate rules (editable, not the last claimant); its `Apply` finds the child by id among all children (an unknown id is the Application's not found) and returns the outcome of the child's method. The child's method (`party.Remove()`) runs the child's step with only the child's rules (active, not removed, unresolved) and raises the child's events in its follow-ups.
- A child collection on the root returns every row, removed ones included (`Parties`, `RiskObjects`); a filtered question is a bool fact on the root (`HasActiveRiskObject`, `HasUnresolvedCriticalIssues`).

## Extending the Domain

Names follow `docs/CODING-STANDARDS.md` 'Naming', folders 'Domain folders'.

- **A new entity in an aggregate:** a private parameterless constructor, a `Details` record, private setters and `internal` mutators; an `internal` operation in `Flows/` with its input in `Inputs/`, and a public root method chaining the event and `Settle`; every precondition as a rule; a stored completeness problem as a rule in the entity's `Rules/` that the issue evaluation checks; tests in the mirrored folders and an entry in `EntityConstructionTests`.
- **A new aggregate:** a top-level folder shaped like `Claims/`, a base input in its `Inputs/` (and a base transition in `Flows/` when it has a lifecycle), a creation operation behind a public static method named by the domain verb that chains its event, the capability interfaces it needs, and other aggregates referenced by id only.
- **A fact from outside the aggregate:** a plain field on the step's input, computed by one Application query; one record only when several fields come together from one aggregate (`ClaimReference`: the claim's id, organisation and state, from `claim.Reference`, to open a reserve component); never a load inside the Domain.
- **State:** a lifecycle is a closed set in a state property (`State`, `ApprovalState`) with an `internal` setter. A move is a transition (Code shapes, above); a change beyond the move is a separate operation the Application runs in the same Unit of Work. The aggregate method raises the state-changed event in a follow-up. Who may move is a rule on the transition (`HasMinimumRole` with the lowest role needed); `UserRole` variants list the roles whose rights they hold, so the nesting is stated once. `OpenClaimTransition` is the reference.

## Provides and expects

- **Provides:** the public aggregate methods (each returns an `Outcome`), the public input records, the domain events, `Finding`, `Move`, `ClaimTransitions.NextFrom`, the closed sets with their `From(kind)`, and the reference values (`PolicyPeriod`, `CauseCodes`, `ClaimReference`).
- **Expects:** every fact it does not hold on the input, computed by the Application (`docs/ARCHITECTURE.md` 'Inputs'); the time and actor stamped once per call; for a document, a finished blob path and the file's first 512 bytes (`Header`); a claim number from the counter.
- **Test fixtures:** claims are built through the public aggregate methods, so a fixture claim is evaluated and has raised its events (`TestClaims`). Two shortcuts bypass them on purpose: `TestClaims.MoveTo` places a claim in a state through a test transition, and `TestClaims.ChangeLoss` sets the loss to skip the after-Draft guard. `TestReserves` builds a component through `ReserveComponent.Open` and a pending row through the submit operation, so a row starts pending unless a test calls the component method (which auto-approves within the limit).
- **Reference examples:** `OpenClaimTransition` (transition); `OpenReserveComponentOperation` and `UploadClaimDocumentOperation` (creation with outside facts); `ReserveComponent.SubmitHistory` (chained aggregate method on a child).
