# AI Workflow

## How I use AI

I use Claude Code in the terminal as an implementation partner under my direction, not as an author working on its own. The behavior is fixed in the repository before any feature work, in `.claude/CLAUDE.md` and `.claude/settings.json`. Claude may not create or edit files unless I ask, approving a plan is not permission to implement it, git writes are mine (Claude gives me the command to run), `gh` writes happen only on my explicit instruction, and ambiguous phrasing is treated as a question. I run Claude Code with permissions bypassed, so protection has two layers: a deny list in `.claude/settings.json` that hard-blocks commands such as git writes, and rules in `CLAUDE.md` and the skills that make Claude ask me in chat before anything else with side effects (migrations, Azure, non-read-only `gh`, deletions). For any problem with more than one reasonable approach, including problems I have not flagged as a choice, Claude gives a few options, each argued (what it does, pros, cons, pitfalls), and ends with a recommendation; I review the options and choose. Business rules come from me and from local copies of the task documents. When a rule is missing, Claude asks instead of inferring one.

Work happens in packs. I pick a topic and ask for a design, which the design skill produces without writing code; we settle the open choices and I approve it. Then I ask for one pack at a time, and Claude implements that pack and stops. Side topics, next steps and ideas that come up along the way are not discussed on the spot: Claude appends them as tagged one-line items to a parking-lot note in `.claude/temp/`, without reading it, so they are not lost and also stay out of my focus and out of Claude's context until I open them. My prompts describe the structure, the format and the outcome I want in terms of functionality and architecture (what a component does, how it fits the layers, what it has to guarantee). They do not dictate code: code style and conventions already live in `CLAUDE.md`, and when the generated code needs adjusting I follow up with small, targeted queries to refactor it. Context between topics lives in committed notes in `.claude/temp/`, so I clear the session and load the relevant note back instead of carrying long conversations.

When a pack is done locally, I review it file by file myself. For the parts that differ from what I expected, or that were written entirely by the agent, I ask Claude to explain the details and the reasoning until I understand all of it. After that I run the code-review skill, which starts a fresh Opus reader with none of the session's context and checks the changes against the conventions, vulnerabilities and defect classes, followed by the passive spec-check, which compares the changed code with the business rules. I run the build and tests and make the commits myself. Decisions go into `docs/ARCHITECTURE.md`, which starts as the original plan and is updated when a decision changes.

To make the workflow faster and more robust I rely on generated files and small pieces of functionality instead of re-explaining things in each session. Each has one fixed format and a defined procedure, so it is idempotent: the same input produces the same result, identifiers stay stable, and nothing depends on how a particular session went. A handful of extra files and roughly 15-20 minutes of setup pay back by making agent development quicker, sharper and more consistent from one session to the next. Three examples:

- **AI journal** (`.claude/temp/notes-ai-journal.md`, written by the ai-journal skill). Append-only, one format: a header `## TYPE-NNN | phase | date` followed by fixed `key: value` lines. Types are PROMPT, CORRECTION, SPLIT, ASSESSMENT and SESSION; counters are never reused, so earlier entries never change. A correction, for instance, is `## CORRECTION-001 | <phase> | <date>` with the keys `what`, `caught-by`, `fix` and `lesson`. `grep "^## "` returns the whole map of entries, and a confidentiality check runs before every write. At the end the skill compiles the correction section, and optional prompt and split lists, from these entries.
- **Rule register and spec-check** (`docs/rules.local.md`, `.claude/skills/spec-check/SKILL.md`). The task documents are kept as local markdown copies, and the register is a trimmed index of them: 151 one-line rules (122 from the spec, 29 from the assessment) in one format, `ID | area | paraphrase | source | flags`, for example `S:BR-R-03 | reserve | ... | spec 7.2 |`. Rules where the two documents disagree carry a `conflict:` flag (22 rules). IDs are source-qualified and stay stable across rebuilds, so the agent looks up a rule without loading the full documents. Code carries the same ID (`[Trait("Rule", "S:BR-R-03")]` on tests, `.WithErrorCode("S:BR-R-03")` on validators). The spec-check skill runs automatically after every code review: it takes the changed files, selects the matching rules, and reports each deviation as missing, untested, deviates, conflict or orphan in a fixed output format, so the same code is always checked against the same rules in the same way.
- **Workflow check** (`.claude/tools/check_workflow.py`). A read-only script, standard library only, that verifies the files above against each other: citations to `CLAUDE.md`, the settings deny rules against a command self-test, the rule register, the journal and parking-lot formats, and overlap with the confidential documents. It prints one line per finding and a summary, and exits 1 on findings. Claude runs it automatically and silently after editing any of these files, after each journal entry, parking-lot append and register rebuild, and when I say I am about to commit; it speaks up only when something is wrong.

## Claude system

- `.claude/CLAUDE.md` - the project rules and conventions, and the single source of truth. Skills cite its sections by name instead of restating them, so rules cannot drift between files.
- `.claude/skills/<name>/SKILL.md` - project skills: design, explore, code-review, dev-log, spec-check, ai-journal.
- `.claude/settings.json` - permissions: the deny list (git writes and forced or destructive branch operations) is the hard layer in every mode; the allow and ask entries (read-only git, build, test and `gh` subcommands; migrations and Azure) apply when a session is not in bypass mode. Approval rules for everything else live in `CLAUDE.md` and the skills.
- `.claude/tools/check_workflow.py` - the read-only consistency check described above; `CLAUDE.md` 'Workflow check' says when it runs.
- `.claude/temp/` - committed working notes named `<kind>-<topic>.md` with a status line: designs, explorations, the general plan, the parking lot, and the AI journal.
- `*.local.md` - gitignored local-only files, never committed: markdown copies of the confidential task documents, the rule register, and a note with the assessment context. Because a clone does not have them, Claude checks for them at the start of a session and prints a single line if any is missing.

## AI correction journal

Cases where the AI was wrong or weak, and how each was corrected, are recorded as they happen in `.claude/temp/notes-ai-journal.md`. This section will be generated at the end by the ai-journal skill (compile mode) from that journal, then reviewed and edited by me.
